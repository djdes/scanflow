## 1. Обязательная актуализация Git (ветки и коммиты)

Разработка и отладка ведутся с нескольких рабочих окружений (локальная машина, сервер `BSQL` `C:\www\ScanFlow`, облачные сессии), а деплой на прод (`https://scanflow.ru`) запускается через GitHub Actions при пуше в ветку `main`.

**Каждый агент обязан начинать КАЖДУЮ новую задачу с проверки GitHub — включая анализ без правок и документацию.** Проверка из предыдущей задачи или сессии не считается. Повторяйте её после длительного перерыва, перед новым этапом длительной работы, каждым коммитом и каждым пушем.

Из корня репозитория выполните команды, дождавшись успешного завершения `fetch`:

```bash
git fetch --all --prune
git status -sb
git branch -vv
git symbolic-ref --short refs/remotes/origin/HEAD
git log --oneline -n 5 HEAD..origin/main
git rev-list --left-right --count HEAD...origin/main
```

Основная ветка ScanFlow — `main`; сверяйте это с `origin/HEAD`. Если ссылки нет, проверьте `git remote show origin`. Для рабочей ветки с удалённым аналогом дополнительно сравните `HEAD` с `origin/<рабочая-ветка>` через `git log` и `git rev-list --left-right --count`.

**`git fetch` обновляет сведения об удалённых коммитах, но не рабочие файлы.** После него оцените отставание/расхождение и актуализируйте рабочую ветку до начала правок. Ошибку `fetch` явно сообщайте и повторяйте проверку после её устранения; до успешной проверки не объявляйте синхронизацию завершённой и не коммитьте/пушьте.

### Сохранность локальной работы

- Перед обновлением сохраните исходный HEAD резервной веткой с уникальным именем: `git branch backup/before-sync-<дата-время> HEAD` (подставьте дату и время). Она сохраняет только коммиты: отдельно учитывайте незакоммиченные и неотслеживаемые файлы по `git status` и `git diff`.
- Если локальные изменения мешают обновлению, сохраните их отдельно или через stash; после обновления проверьте восстановление. При `--autostash` также проверьте, что изменения восстановлены и конфликтов не осталось.
- Не удаляйте чужие файлы и изменения ради синхронизации или чистого статуса. Если `main` разошлась с `origin/main`, изучите обе стороны и сохраните уникальные коммиты; не обходите ошибку `--ff-only` через `reset --hard` или force push.

### Правила работы с ветками и коммитами:
1. **Всегда синхронизируйте `main` с `origin/main` перед правками:**
   - Если вы находитесь на устаревшей локальной ветке (например, `feat/*`, из которой ранее пушили напрямую в `origin/main` через `git push origin HEAD:main`), переключитесь на `main` и подтяните актуальные коммиты:
     ```bash
     git checkout main
     git pull --ff-only origin main
     ```
   - Если работа ведётся в отдельной ветке в другом рабочем окружении, актуализируйте её через `git pull --rebase --autostash origin main`, учитывая также её удалённый аналог. Разбирайте конфликты с сохранением актуальных инструкций и уникальных правок; после rebase проверяйте восстановление autostash.
2. **Не оставляйте локальную `main` позади `origin/main`:**
   - При пуше из рабочей ветки в `main` обновляйте и локальную ветку `main` (`git fetch origin main:main`), а на сервере `BSQL` (`C:\www\ScanFlow`) держите активной ветку `main`, синхронизированную с `origin/main`.
3. **Перед коммитом и пушем повторяйте проверку, после пуша проверяйте результат:**
   - Снова выполните `git fetch --all --prune`, `git status -sb`, `git branch -vv`, сравните рабочую ветку с `origin/main` и её удалённым аналогом, просмотрите `git diff` и `git diff --cached`. Если пришли новые коммиты, интегрируйте их и повторите затронутые проверки.
   - После успешного пуша выполните `git fetch --all --prune` и проверьте совпадение отправленного коммита с целевой удалённой веткой. Команда `git fetch origin main:main` из пункта 2 применима только к неактивной локальной `main`; для активной используйте `git pull --ff-only origin main`.
   - В итоговом ответе указывайте текущую ветку, результат синхронизации и наличие оставленных локальных правок. Постоянный фоновый `pull` не требуется: проверки выполняются на границах задач и этапов.
4. **Никаких правок на боевом сервере мимо `main`:**
   - Любые изменения на `scanflow.ru` доставляются только через коммит и пуш в `origin/main` (GitHub Actions `Deploy to scanflow.ru`).

## 2. Ключевые инварианты проекта (кратко, подробно в `CLAUDE.md`)

- **Синхронизация каталогов 1С — напрямую по MCP (`src/integration/onecCatalogMcp.ts`):**
  - Компания `1` (`admin`) синхронизируется с базой **1С MAG** (`/mcp-1c/hs/mcp-1c`, пользователь `Админ`).
  - Компания `3` (`zakupki`) синхронизируется с базой **1С SUB** (`/mcp-1c-subprod/hs/mcp-1c`, пользователь `Директор`).
  - Синхронизация запускается автоматически при деплое, при старте сервера, каждые 30 минут по расписанию, после создания документа в 1С и по кнопке «Синхронизировать с 1С» (`POST /api/nomenclature/sync-mcp`). Выгружаются все активные позиции и все папки (`ЭтоГруппа = Истина`), кроме помеченных на удаление и 5 архивных категорий (`Списанное`, `Резерв Сезонное`, `SubExpress-Архив`, `РЕЗЕРВ`, `ПРОРАБОТКА`).
- **Безопасность тестов БД:** тесты никогда не должны подключаться к не-тестовой БД (`DB_HOST` только `localhost`/`127.0.0.1`, `DB_NAME` обязан содержать `test`).
- **Секреты:** никогда не коммитьте `.env`, `google-credentials.json`, `certs/*`, реальные ключи API и токены в отслеживаемые файлы (CI-шаг `Secret scan` блокирует деплой).
