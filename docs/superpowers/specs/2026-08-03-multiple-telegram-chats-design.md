# Несколько Telegram chat_id на аккаунт — design

- **Дата:** 2026-08-03
- **Статус:** согласован, к реализации
- **Повод:** уведомления уходят ровно в один чат (`users.telegram_chat_id`). Нужно указывать несколько получателей за раз, а не заводить их по одному. PF-задача `cedfb495` (дедлайн 2026-08-07).

## 1. Главная сложность — «живой пузырь» накладной

Прогресс по накладной показывается ОДНИМ сообщением, которое редактируется по мере событий (`telegramNotifier.sendInvoiceNotification` → `editMessageText`). Его id лежит в `invoices.telegram_message_id` — **одно число на накладную**.

Telegram адресует сообщение парой `(chat_id, message_id)`, и в каждом чате id свой. То есть при нескольких получателях одной колонки принципиально не хватает: во второй чат пузырь либо не отредактируется, либо начнёт сыпать новыми сообщениями на каждое событие.

Поэтому пары «чат → сообщение» переезжают в отдельную таблицу. Это и есть основная часть работы; сам список чатов — мелочь рядом с этим.

## 2. Модель данных (миграция 59, аддитивная, идемпотентная)

**Список чатов.** `users.telegram_chat_id` VARCHAR(64) → `TEXT`, хранит **список id через запятую**. Одиночный id остаётся валидным значением, поэтому миграция данных не нужна и старые аккаунты продолжают работать как раньше.

Отдельную таблицу под чаты не заводим: список короткий (единицы записей), правится целиком одной формой, и join'ов по нему нет — колонка проще и дешевле.

**Пузыри.** Новая таблица:

```sql
CREATE TABLE invoice_telegram_messages (
  invoice_id  INT NOT NULL,
  chat_id     VARCHAR(64) NOT NULL,
  message_id  INT NOT NULL,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (invoice_id, chat_id),
  CONSTRAINT fk_itm_invoice FOREIGN KEY (invoice_id) REFERENCES invoices(id) ON DELETE CASCADE
)
```

`PRIMARY KEY (invoice_id, chat_id)` — в одном чате у накладной ровно один пузырь. `ON DELETE CASCADE` — удалили накладную, записи ушли следом.

**Бэкфилл существующих пузырей обязателен.** Без него у всех накладных с уже отправленным уведомлением пузырь потеряется и на следующем событии придёт дубль. Переносим `invoices.telegram_message_id` в новую таблицу, привязывая к текущему чату владельца:

```sql
INSERT IGNORE INTO invoice_telegram_messages (invoice_id, chat_id, message_id)
SELECT i.id, u.telegram_chat_id, i.telegram_message_id
FROM invoices i JOIN users u ON u.id = i.owner_user_id
WHERE i.telegram_message_id IS NOT NULL
  AND u.telegram_chat_id IS NOT NULL AND u.telegram_chat_id <> ''
```

Строка `invoices.telegram_message_id` **остаётся** (не удаляем колонку): она ничего не ломает, а её удаление — необратимая операция ради косметики.

## 3. Рассылка

`sendInvoiceNotification` принимает `chat_ids: string[]` вместо одного и обходит их по очереди:

- **срочные события** — простое сообщение в каждый чат;
- **прогресс** — для каждого чата свой пузырь: есть запись в `invoice_telegram_messages` → `editMessageText`, нет → `sendMessage` + запись пары.

**Ошибка по одному чату не должна ронять остальные.** Пользователь мог удалить бота из одного чата — остальные обязаны получить уведомление. Каждый чат обрабатывается в своём try/catch, ошибки логируются и глотаются (контракт модуля «никогда не бросать» сохраняется).

`MessageGoneError` (сообщение удалили) уже обрабатывается — отправляем новое и **перезаписываем** пару для этого чата.

Рассылка последовательная, не параллельная: у Telegram есть лимиты на бота, а чатов единицы — выигрыш от параллельности нулевой, риск словить 429 реальный.

## 4. API и валидация

`GET /api/profile` отдаёт `telegram_chat_id` как и раньше (строка со списком) — фронт сам разбирает. Ломать форму ответа не нужно.

`PATCH /api/profile` принимает `telegram_chat_id` строкой со списком, разделители — запятая, точка с запятой, пробел, перевод строки. Нормализуем в «id через запятую». Валидация:

- каждый элемент — целое число, возможно со знаком минус (у групп id отрицательные) — существующий `CHAT_ID_RX` расширяем;
- дубликаты убираем, порядок сохраняем;
- не больше 20 чатов — защита от вставки мусора;
- пустая строка → `null` (уведомления выключены), как сейчас.

`POST /api/profile/test-telegram` шлёт тестовое сообщение **во все** чаты и возвращает поштучный результат: в какой ушло, в какой нет и почему. Иначе при пяти чатах непонятно, какой из них настроен неверно.

`POST /api/profile/lookup-telegram-chat-id` не трогаем: он ищет один chat_id и возвращает его — пользователь добавляет найденный к списку сам.

## 5. UI (страница «Профиль»)

Поле chat_id становится многострочным (`textarea`) с подписью «по одному id в строке или через запятую». Рядом — счётчик распознанных id, чтобы человек видел, что ввод разобрался как ожидалось.

Результат теста показываем построчно: `✓ 123456789` / `✗ -100987 — bot was kicked`.

## 6. Что проверяем

- миграция 59 идемпотентна, бэкфилл переносит существующие пузыри;
- список парсится из любых разделителей, дубликаты схлопываются, мусор отвергается 400;
- прогресс-событие редактирует пузырь в каждом чате, а не плодит новые;
- недоступный чат не мешает доставке в остальные;
- новый чат, добавленный после создания накладной, получает свой пузырь на следующем событии;
- тестовое сообщение возвращает поштучный результат.
