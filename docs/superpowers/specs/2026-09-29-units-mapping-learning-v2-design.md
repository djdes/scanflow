# Пакет v2: количество/единицы, сопоставление, самообучение — дизайн

- **Дата:** 2026-09-29
- **Статус:** согласован (пункты 1–4, 7–20 из анализа 29.09; пункты 5 и 6 — аудит единиц 1С и разбор истории — исключены заказчиком)
- **Повод:** в 1С перестали грузить накладные: «количество не верное либо товар не верный определяется». Анализ прода 29.09 (124 накладные, 1205 строк):
  - у 21% строк единица в накладной ≠ единице позиции в 1С; в уже отправленных — 99 из 482;
  - накладная 194 ушла в 1С с 50 000 кг творога (×1000), «Сахар 500×5г» → 500 кг, яйца «С1 360шт» → 1080 **кг** (8 накладных);
  - «выученное» правило `item_unit шт→кг` переписывает единицу у **всех** строк поставщика (СВИТ ЛАЙФ, ВЕСЕЛОФФ, Вкусный мир);
  - выгрузка каталога из 1С пачками по 500 после первой пачки **удаляет** сопоставления позиций второй пачки (`onec.ts:272`, `mappingRepo.removeOrphaned`) — у второй компании из 11 ручных сопоставлений уцелело одно;
  - выбор LLM перекрывает и перезаписывает сохранённые правила; `approved` нигде не читается; счётчики использования мертвы;
  - правки пользователя (количество, цена, сопоставление) не журналируются — учиться не на чем.
- **Требование заказчика к безопасности:** «если что-то будет не так — вернуться хотя бы к правильным суммам, НДС и номерам счетов».

   Прод — **MariaDB 10.11** (не MySQL 9.6, как было в CLAUDE.md; MySQL только локально). Новый SQL пишем переносимо: без `ADD COLUMN IF NOT EXISTS` (только `hasColumn`-guard), без JSON-типа (TEXT/MEDIUMTEXT), без DEFAULT у TEXT.
2. **Ежедневный бэкап БД** из приложения (сейчас `backupDatabase()` — no-op, внешнего cron нет): логический дамп через mysql2 в `data/backups/scanflow-YYYY-MM-DD.sql.gz`, хранить 14 дней.
3. **Снимки шапки и строк** — таблица `invoice_snapshots`:
   - `kind='baseline'` — бэкфилл миграцией для всех накладных на момент выкладки (номер, дата, сумма, НДС, поставщик, ИНН + строки JSON);
   - `kind='recognized'` — пишется при каждом распознавании/перераспознавании **до** пересчёта единиц.
   API и кнопка «Вернуть номер/дату/сумму/НДС как при распознавании (или как до v2)»; админский массовый откат шапок.
4. **Флаги движков** в `analyzer_config.engine_flags` (TEXT с JSON), переключаются в «Настройки → Движки v2» (только admin). Выключенный флаг = прежнее поведение кода (старые функции сохраняются):

5. **Инварианты денег:** пересчёт единиц никогда не меняет `total` строки и шапку (`total_sum`, `vat_sum`, `invoice_number`, `invoice_date`). Тест-инвариант + runtime-проверка.
6. Ранбук отката: `docs/runbooks/rollback-v2.md`.

## 1. Количество и единицы (пункты 1–4)

### 1.1 Единый конвертер (п.1)
Новый модуль `src/mapping/unitConverter.ts` — чистые функции; `src/services/lineConversion.ts` — обёртка с правилами из БД и флагом.
- В `invoice_items` храним **как в накладной**: `raw_quantity`, `raw_unit`, `raw_price`, `raw_total` (после OCR/исправлений/НДС-санитайзеров, до пересчёта) и результат пересчёта: `conv_factor`, `conv_note` («60 шт × 0,4 кг = 24 кг»), `conv_source` (`same`, `scale`, `rule`, `name`, `name_count`, `price_fit`, `legacy`, `manual`), `qty_flag` + `qty_flag_note`.
- Конвертер **всегда считает от raw** → идемпотентен (повторный `/remap` не умножает второй раз).
- Все пути (приём, многостраничная склейка, перераспознавание, «дофоткать», диспетчер, `/remap`, `/llm-remap`, ручной выбор позиции, правка строки) вызывают одну функцию `convertLine()`. При `units_v2=off` она вызывает прежний `resolveAndApplyPackTransform`.
- Округление: количество — 3 знака, цена — 4 знака, сумма — как в накладной.
- UI: в строке под количеством — «как в накладной: 60 шт × 32,20» и формула; кнопка «Вернуть как в накладной».

### 1.2 Модель упаковки (п.2)
`parsePack(name)` разбирает название:
- мера: `0,4 кг`, `600г`, `1,5л`, `420мл`; **диапазон** `4-5кг`, `15-25кг`, `300-500г` → не вес упаковки (переменный вес / калибр);
- нетто/брутто: `10л/9,6кг` (при учёте в кг берём массу), `сух.вес 4кг` (помечаем как «сухой вес», по умолчанию берём номинал);
- количество в упаковке: `240г×24`, `24*240г`, `10х1кг`/`10x1кг`, `500*5г`, `1/12`, `(х50/1000)`, `*100/2500`, `100шт/упак`, `10пач/упак`.

Пересчёт по классам единиц (СЧЁТ: шт/упак/кор/бут/бан/пач/рул/меш/ведро…; МАССА: кг/г; ОБЪЁМ: л/мл):
- одинаковые → ×1; масса↔масса, объём↔объём → масштаб; л→кг ×1 (с пометкой «плотность не учтена»);
- СЧЁТ → МАССА/ОБЪЁМ: правило (п.3) → иначе мера из названия (× количество в упаковке, если единица накладной — кор/упак/ящ); только диапазон → флаг `needs_weight` без пересчёта;
- СЧЁТ → СЧЁТ: упак/кор → шт × «шт в упаковке» из названия (исправляет «2 упак перчаток по 100 шт» → 200 шт); шт → шт ×1;
- МАССА → СЧЁТ: если в названии вес штуки и результат ≈ целое (±5%) — делим; иначе флаг `unit_mismatch`;
- нет 1С-единицы — не пересчитываем (только канонизируем написание).
Если есть несколько кандидатов (вес штуки vs вес коробки), выбирает проверка цены (п.4), иначе — правило по умолчанию и флаг.

### 1.3 Правила единиц «поставщик + товар» (п.3)
- `ocr_correction_cards` получает `item_key` и `active`. Исправление единицы запоминается **только для этого товара** этого поставщика и применяется к сырой единице. Три действующих правила «на весь поставщик» миграцией выключаются (`active=0`, не удаляются — для отката).
- Новая таблица `item_unit_rules` (owner, supplier_key|NULL, name_key, raw_unit|NULL, target_unit, factor, source `user|miner|llm|legacy`, active, times_used, …) — правило пересчёта для товара. Старые `pack_size/pack_unit` на сопоставлениях используются только если соответствующая мера реально есть в названии (гасит «протекание» упаковок между размерами); новые упаковки на глобальные сопоставления больше не пишутся.
- Правка количества в UI, когда единицы накладной и 1С разного класса, предлагает «Запомнить: 1 шт «…» = 0,4 кг у этого поставщика» → `item_unit_rules`.

### 1.4 Проверка правдоподобия (п.4)
- Медиана цены за единицу 1С по позиции считается устойчиво (без строк с `qty_flag`, с отбрасыванием выбросов ×5 от медианы).
- После пересчёта: цена отличается от медианы ≥3× в любую сторону → `qty_flag='price_outlier'`; если альтернативный кандидат пересчёта попадает в ×0,5…×2 от медианы — берём его (`conv_source='price_fit'`, в заметке «подобрано по истории цен»).
- Флаг: строка красная; «−10% и дешевле» больше не зелёные, если есть флаг; автопилот держит накладную (`qualityGate`: `unit_suspect`); отправка в 1С вручную — с подтверждением.

## 2. Сопоставление и сохранение правил (пункты 7–13)

- **п.7** Выгрузка каталога не удаляет правила: `/nomenclature/sync` и импорт больше не зовут `removeOrphaned`. Сопоставления с исчезнувшей позицией помечаются `orphaned_at` (не удаляются) и пропускаются при подборе; очистка — только вручную. Разовое восстановление: правила из старых дампов (24.06, 22.07), чьи позиции есть в текущем каталоге, возвращаются с `source='restored'` без подтверждения.
- **п.8** У сопоставления: `source` (`user|supplier|import|llm|fuzzy|restored|history`), `confirmed_at/confirmed_by`, живые `times_seen/last_seen_at`. Порядок: правило поставщика → подтверждённое правило (точное имя → `name_key`) → выбор LLM (с проверками п.10–11) → неподтверждённое правило → fuzzy. LLM **не перезаписывает** подтверждённые правила. Ручной выбор = подтверждение (+ уверенность строки 1.0). Кнопка «Подтвердить сопоставления» на накладной.
- **п.9** `name_key` — нормализованный ключ товара (регистр, ё, пунктуация, числа «7,5 кг»→`7.5кг`, без «ГОСТ», «1/12», «(х50/1000)», порядок слов не важен). Хранится на сопоставлениях и правилах поставщика, поиск: точное имя → ключ.
- **п.10** Жёсткие атрибуты: объём, габариты (179х132х46), размер S/M/L/XL, жирность %, калибр 21/25, артикул-коды (К-139, СпК-115). Если атрибут есть с обеих сторон и не совпал — кандидат отклоняется (fuzzy/токены), выбор LLM понижается до подсказки (уверенность 0,5, флаг). Порог word-overlap 0,5 → 0,6.
- **п.11** «Не это»: `mapping_rejections` (owner, name_key, onec_guid). Пишется при замене/очистке сопоставления; исключает кандидата во всех стадиях и для LLM.
- **п.12** «Новые товары»: страница со строками без позиции 1С, сгруппированными по `name_key`. Действия: сопоставить группу с существующей позицией (правило), или «Создать в 1С» (имя, единица, группа) → в выгрузке `/pending` строка несёт `new_item {name, unit, parent_guid}`; модуль 1С (обновление .epf) создаёт позицию с этой единицей/группой.
- **п.13** Холодный старт: после синхронизации каталога (дебаунс 2 мин) — автоматическое пересопоставление неотправленных накладных; для строк с уверенностью < 0,8 — топ-3 кандидата «в один клик» (клик = подтверждённое правило).

## 3. Самообучение (пункты 14–17)

- **п.14** `edit_log`: кто/когда/что «было → стало» по накладной, строке, сопоставлению, единице, поставщику, откатам; вкладка «История» показывает правки.
- **п.15** Ночной разбор (03:00 МСК, флаг `learning`; кнопка «Разобрать сейчас»): детерминированный майнер по `edit_log` + флагам п.4 (повторяющиеся правки единиц/количества → правило пересчёта; выбросы цены → вероятный вес упаковки) + Claude API для неразобранных аномалий (≤30 за ночь). Результат — `rule_proposals`; страница «Предложения правил»: принять (создаёт правило и перепересчитывает неотправленные накладные) / отклонить.
- **п.16** Память распознавания: в системный промпт Claude (кэшируемый блок рядом с каталогом) добавляется «Памятка по поставщикам» из принятых правил (единицы, упаковки, варианты ИНН) — до ~3k токенов.
- **п.17** Эталоны: флаг `invoices.golden` («⭐ В эталоны»); фото эталонов не удаляются через 90 дней; прогон эталонов (по кнопке, админ) заново распознаёт фото текущей моделью/промптом без записи в накладные и сравнивает номер, дату, сумму, НДС, ИНН, строки; результаты — `golden_runs`.

## 4. Поставщики и эксплуатация (пункты 18–20)

- **п.18** Проверка контрольной суммы ИНН при сохранении карточки и правке накладной; бейдж «ИНН не проходит проверку» у карточек; «Объединить карточки» (накладные перепривязываются, правила поставщика переносятся, удалённая карточка сохраняется в `edit_log`). При автопривязке карточки с невалидным ИНН не участвуют, двойники с одинаковым названием — берётся валидный.
- **п.19** Пакетный режим уведомлений (флаг `batch_notify`): ≥3 загрузки за 2 мин от одного пользователя → отдельные сообщения копятся и уходят одной сводкой через 90 с тишины; сводка = одна отправка для лимита. «message is not modified» — не ошибка.
- **п.20** Опрос 1С пишется в журнал только при непустой очереди или раз в час; старые записи `poll` чистятся (3 дня). Мусорные URL (`%c0%ae`) → 400 без error-лога. `sync-flag` не пишем в `api_requests_log`.

## 5. Откат

| Что пошло не так | Что делать |
|---|---|
| Неверный пересчёт количества | «Настройки → Движки v2» → выключить `units_v2`/`price_guard`; в накладной «Вернуть как в накладной»; `/remap` пересчитает старым движком |
| Неверное сопоставление | выключить `mapping_v2` (старый порядок стадий) |
| Номер/дата/сумма/НДС изменились | кнопка в «Истории» или `POST /api/debug/restore-headers` (из `recognized` или `baseline`) |
| Всё плохо | деплой тега `backup/pre-v2-2026-09-29` + восстановление дампа (новые таблицы/колонки старому коду не мешают) |
