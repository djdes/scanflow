# Повышение точности OCR-распознавания накладных (Claude API)

**Дата:** 2026-07-09
**Статус:** утверждён (вариант B из брейншторма)

## Проблема

Основные жалобы на качество распознавания в режиме `claude_api` (Sonnet 5):

1. **Неверные цифры/суммы** — quantity/price/total перепутаны между колонками, лишние нули, НДС взят из промежуточного «Итого».
2. **Искажённые названия и шапка** — названия товаров коверкаются, поставщик/номер/дата неверные.

Технические причины, найденные в текущей реализации (`src/ocr/claudeApiAnalyzer.ts`):

- `max_tokens: 4096` (single) / `8192` (multi). На Sonnet 5 adaptive thinking включён по умолчанию (параметр `thinking` в коде не передаётся), и размышления расходуют тот же бюджет `max_tokens` → на плотных накладных ответ обрезается посреди JSON.
- Весь промпт (~3k токенов) + каталог номенклатуры (~12k токенов) передаются в user-сообщении при каждом вызове: нет prompt caching, инструкции не имеют веса system-роли.
- JSON извлекается regex'ом и чинится `jsonrepair` — вместо гарантированного structured output API.
- Секция «самопроверка» в промпте просит модель пересчитать арифметику, но никто не проверяет, сделала ли она это.

## Решение (два уровня)

### Уровень 1 — перестройка запроса (без дополнительных вызовов)

Все изменения в `src/ocr/claudeApiAnalyzer.ts`, функции `analyzeImageWithClaudeApi`, `analyzeMultipleImagesWithClaudeApi`, `analyzeMultiPageTextWithClaudeApi`.

**1.1. System prompt + prompt caching.**

- Статичные инструкции (структура ТОРГ-12/УПД, карта колонок, правила чтения цифр, правила названий, правила НДС и multi-page) переезжают в `system` как массив блоков.
- Блок 1: инструкции, `cache_control: {type: "ephemeral"}`.
- Блок 2: каталог номенклатуры (если LLM-маппер включён), свой `cache_control` breakpoint. Каталог меняется редко → кэш живёт между накладными.
- User-сообщение: изображение(я) + короткая задача («одна страница» / «объедини N страниц, текст ниже»).
- Экономика: повторные вызовы читают ~15k токенов кэша по ~0.1× цены — дешевле текущего состояния.

**1.2. Structured outputs.**

- Вместо «верни строго JSON» → `output_config: {format: {type: "json_schema", schema: INVOICE_SCHEMA}}`.
- `INVOICE_SCHEMA` повторяет текущий формат ответа: `invoice_type`, `invoice_number`, `invoice_date`, `supplier`, `supplier_inn`, `supplier_kpp`, `supplier_bik`, `supplier_account`, `supplier_corr_account`, `supplier_address`, `total_sum`, `vat_sum`, `items[]` (`name`, `quantity`, `unit`, `price`, `total`, `vat_rate`, `row_no`, `pack_size`, опционально `catalog_idx`). Все объекты с `additionalProperties: false`, nullable-поля через `["number", "null"]` и т.п.
- Ограничения structured outputs учитываем: без `minimum`/`maxLength` (валидация — на сервере, п. 2), без рекурсии.
- `safeParseClaudeJson`/`jsonrepair` для claude_api-пути удаляются (JSON гарантирован API). Legacy hybrid-путь и `mapItemsWithClaudeApi` не трогаем.

**1.3. Thinking и бюджет токенов.**

- `thinking: {type: "adaptive"}` задаётся явно.
- `max_tokens: 16000` для одиночной страницы (non-streaming допустимо), `32000` для многостраничных — через `client.messages.stream()` + `finalMessage()` (SDK требует streaming для больших `max_tokens`).
- Таймауты `withRetry` не меняются.

**1.4. Переработка текста промпта.**

Доменная логика сохраняется полностью (карта колонок ТОРГ-12, упаковочные подсказки `*48`/`1/12`, правила НДС из итоговой строки, multi-page правила). Реструктуризация под Sonnet 5 (следует инструкциям буквальнее):

- Секция **«дисциплина чтения цифр»**: короткие жёсткие правила — «2,000» = 2 шт (запятая = десятичная), «2 000» = 2000; quantity > 4 цифр запрещён (это код товара); price = колонка «с НДС», НЕ колонка 4; total = самая правая колонка строки.
- Секция **«точность названий»**: кириллица как есть (UTF-8), вес/объём/упаковочные подсказки сохраняются дословно, бренды/артикулы убираются; если фрагмент названия нечитаем — не выдумывать, переписать читаемую часть.
- Секция «самопроверка» сокращается до перечня инвариантов (qty×price≈total, Σtotal≈total_sum) — подробный пересчёт делает adaptive thinking, страхует серверная валидация.

### Уровень 2 — серверная валидация + точечное до-чтение

**2.1. Новый модуль `src/ocr/invoiceValidator.ts`** — чистая функция без I/O:

```ts
interface ValidationIssue {
  code: 'row_math' | 'qty_digits' | 'total_mismatch' | 'vat_mismatch'
      | 'inn_checksum' | 'kpp_format' | 'date_range';
  rowNo?: number;          // для строчных проверок
  message: string;         // человекочитаемо, по-русски — уходит в repair-промпт
}
function validateParsedInvoice(data: ParsedInvoiceData): ValidationIssue[]
```

Проверки:

| Код | Правило |
|---|---|
| `row_math` | по каждой строке `quantity × price ≈ total` (допуск ±1%) |
| `qty_digits` | `quantity` ≤ 4 значащих цифр (SKU-коды не могут быть количеством) |
| `total_mismatch` | `Σ items.total ≈ total_sum` (±1 ₽); пропускается, если `total_sum === null` (промежуточный лист) |
| `vat_mismatch` | `vat_sum ≈ Σ(total × ставка/(100+ставка))` (±2%); только если есть и `vat_sum`, и ставки |
| `inn_checksum` | контрольная сумма ИНН (10 цифр — 1 контрольная, 12 цифр — 2) |
| `kpp_format` | КПП — ровно 9 цифр либо null |
| `date_range` | `invoice_date` в диапазоне [сегодня − 2 года; сегодня + 7 дней] |

**2.2. До-чтение (repair call).**

Обёртка `analyzeWithVerification(...)` в `claudeApiAnalyzer.ts`:

1. Основной вызов (уровень 1) → `validateParsedInvoice`.
2. Если issues пуст — готово.
3. Иначе — **один** дополнительный вызов: тот же system (cache hit), то же изображение, user-сообщение = первый JSON + список issues («в строке 3 quantity×price = 1240, а total = 12400 — перечитай строку 3 на фото») + просьба вернуть полный исправленный JSON по той же схеме.
4. Повторная валидация. Если issues стало строго меньше — берём исправленный результат, иначе оставляем первый.
5. Максимум одно до-чтение, без циклов. Остаточные расхождения помечаются существующим флагом `items_total_mismatch` — как сейчас.

Логирование: winston-лог с перечнем issues, фактом repair-вызова и результатом (fixed/partial/unchanged) — для оценки эффективности по логам.

**2.3. Интеграция.**

`ocrManager.ts` вместо прямых `analyzeImageWithClaudeApi`/`analyzeMultipleImagesWithClaudeApi`/`analyzeMultiPageTextWithClaudeApi` вызывает их verification-обёртки. Сигнатуры результата (`ApiAnalyzerResult`) не меняются. `suppliers.ts` (распознавание реквизитов) и скрипты продолжают звать «сырые» функции.

## Что не меняется

- Схема БД (миграций нет), UI, интеграция с 1С, Telegram-уведомления.
- Legacy hybrid-режим (Google Vision → Claude text), `mapItemsWithClaudeApi`, `buildSupplierPrompt`.
- Все пункты «Things future-Claude must not break» из CLAUDE.md, включая п. 3 (кросс-валидация qty×price≈total — она усиливается, не ослабляется) и п. 4 (quantity ≤ 4 цифр).
- Модель — `claude-sonnet-5` (Opus не используется: дорого, решено на брейншторме).

## Стоимость

- Идеальная накладная: 1 вызов, вход дешевле текущего за счёт кэша (~0.1× на ~15k токенов промпта+каталога), выход чуть дороже за счёт thinking. Итого ≈ текущая цена или ниже.
- Проблемная накладная (ожидаемо 20–30%): +1 вызов с кэшированным system — примерно +50–70% к цене этой накладной.

## Тестирование

- Юнит-тесты `tests/ocr/invoiceValidator.test.ts` — чистая функция, без БД и сети: каждая проверка на позитив/негатив, включая контрольные суммы ИНН на реальных валидных/битых номерах.
- Юнит-тест на построение `INVOICE_SCHEMA`/system-блоков (структура запроса, наличие cache_control).
- Компиляция: `tsc --noEmit` (локально `npm test` запрещён — прод-БД, см. CLAUDE.md п. 17; vitest — только с `DB_NAME=scanflow_test`).
- Ручная проверка: `npm run test:pipeline -- <фото>` на 3–5 реальных накладных из `data/` (включая одну плотную и одну многостраничную), сравнение сумм с бумагой.

## Риски

- **Structured outputs + первая компиляция схемы**: первый запрос с новой схемой медленнее (одноразовая компиляция, потом 24-часовой кэш схемы). Приемлемо.
- **Кэш инвалидируется при изменении каталога** — это штатно: первый вызов после синка каталога платит полную цену записи кэша.
- **Repair-вызов может «исправить» верное значение**: защита — принимаем результат только при строгом уменьшении числа issues.
- **`stop_reason: max_tokens` при огромных накладных**: с 16k/32k практически исключено; при срабатывании логируем и падаем в текущий error-путь (как сегодня).
