- **Статус:** согласован, готов к плану реализации

| Спека | Статус | Что берём |
|---|---|---|

| [`2026-06-24-per-tenant-suppliers-design.md`](2026-06-24-per-tenant-suppliers-design.md) | черновик, не начата | **решение по ключу поставщиков принимаем как есть** (Вариант A, см. 7.1) |

**Три решения меняются относительно черновиков** — зафиксировано здесь, чтобы расхождение не всплыло при реализации:

1. **`analyzer_config` целиком остаётся платформенным.** Спека по интеграциям оставляла открытым продуктовый вопрос и предлагала вынести `auto_send_1c`, `auto_send_sber`, `dadata_api_key` в пер-тенантные. Решение владельца продукта (2026-07-22): вкладка «Настройки» — только для админа и действует на всех (см. 4.1). Значит перенос не делаем; пер-тенантным становится только **подключение** к Сберу (`sber_tokens`), а не тумблеры.
2. **Флаг `DATA_SCOPING_ENABLED` удаляется.** Черновики предлагали переиспользовать флаг для поэтапной выкатки. Именно флаг, выключенный по умолчанию, и есть механизм, позволяющий выкатиться без изоляции, — поэтому изоляция становится безусловной.
3. **Сквозной доступ роли `admin` убирается.** Черновики его сохраняли. Теперь админ видит только свою компанию, сохраняя доступ к платформенным настройкам.

## 1. Контекст

Каждый аккаунт сервиса — отдельная компания. Фактически изоляция сделана только для накладных, а справочники, банковское подключение, уведомления и фоновые действия остались общими на всю установку. Поводом стала регистрация второй компании (`zakupki`), которая сразу увидела данные первой.

## 2. Что подтверждено на проде

Проверено под аккаунтом второй компании (роль `user`, одна своя накладная от 2026-07-22).

| Область | Состояние | Доказательство |
|---|---|---|
| Накладные | **изолированы корректно** | `GET /api/invoices/stats` → `total: 1`, видна только своя накладная |
| Поставщики | **течёт** | видно 14 чужих поставщиков с расчётными счетами, БИК, корсчетами; `last_used_at` — июнь–начало июля, до появления аккаунта |
| Номенклатура 1С | **течёт** | виден чужой каталог |
| Сбербанк | **течёт** | `GET /api/sber/status` → `connected: true` при том, что своё подключение не заводилось |
| Уведомления | **течёт** | скан в новой компании прислал сообщение в Telegram-бот первой компании |

Важно для истории: изначально был сделан вывод, что течёт и список накладных. Это оказалось ошибкой измерения (запрос с `limit=3` показал собственную накладную аккаунта). `DATA_SCOPING_ENABLED` на проде включён, скоупинг накладных работает. Область работ от этого сужается — `invoices` и всё, что висит на `invoice_id`, переделывать не нужно.

## 3. Корневая причина

Две независимые причины, обе — следы однопользовательской архитектуры.

**3.1. У таблиц справочников нет колонки владельца.** `suppliers` (PK `inn`), `onec_nomenclature` (PK `guid`), `nomenclature_mappings` (`scanned_name` UNIQUE глобально), `nomenclature_price_stats` (PK `onec_guid`), `sber_tokens` (`CHECK (id = 1)` — физически одна строка на установку). Изоляция здесь невозможна в принципе, пока не появится ключ арендатора.

**3.2. `userRepo.firstUserId()` используется как замена арендатора.** Пять мест берут «первого пользователя» там, где нужен владелец накладной:

| Место | Что делает | Последствие |
|---|---|---|
| `src/notifications/events.ts:31` | получатель уведомления при `triggeredByUserId = null` | события фоновых процессов уходят первой компании |
| `src/notifications/events.ts:159` | `notifySupplierExtractError` | то же |
| `src/watcher/fileWatcher.ts:196` | `autoSendSber` берёт API-ключ первого админа | автоплатёж по чужой накладной уходит со счёта первой компании |
| `src/api/routes/invoices.ts:1691` | шаблон назначения платежа | в платёжку подставляется шаблон чужой компании |
| `src/api/routes/dispatcher.ts:85` | контекст диспетчера | фоновые действия от имени первой компании |

**3.3. Усугубляющие факторы.**

- `NomenclatureMapper` хранит кэш каталога в шести полях единственного экземпляра на процесс (`onecFuse`, `learnedTokens`, `onecTokenIndex`, `onecIdf`, `onecDf`, `onecExactIndex`). Даже после правки SQL каталог протечёт через память, если кэш не разделить по владельцу.
- `auto_send_sber` лежит в `analyzer_config` — платформенной таблице, и это по замыслу (см. 4.1). Опасен не сам глобальный тумблер, а то, что действие выполняется не в контексте владельца: в сочетании с 3.2 и единственной строкой `sber_tokens` включённый автоплатёж оплачивает накладные любой компании со счёта первой.

## 4. Принятые решения

| Вопрос | Решение |
|---|---|
| Модель компании | **Аккаунт = компания.** Владелец — `users.id`, колонка `owner_user_id`. Отдельной таблицы `companies` не заводим. |
| Роль `admin` | Видит **только данные своей компании** — сквозной bypass по роли убирается. За админом остаётся доступ к платформенным настройкам (модели обработки и т.д.), влияющим на всех. |
| Флаг | `DATA_SCOPING_ENABLED` **удаляется**, изоляция всегда включена. Флаг по умолчанию `false` — это и есть механизм, из-за которого возможна выкатка без изоляции. |

Следствие по ролям: `admin` — оператор платформы, который вдобавок владеет своей компанией. Обычные компании заводятся с ролью `user`. Кросс-тенантного доступа не имеет никто; для поддержки при необходимости заводится отдельная роль позже (вне области этой работы).

### 4.1. Профиль против настроек

Разделение конфигурации закрепляется явно — это опорное правило для всей работы.

| | Вкладка «Профиль» | Вкладка «Настройки» |
|---|---|---|
| Кому | каждой компании своё | только `admin` |
| На кого влияет | только на свою компанию | на **все** компании |
| Роут | `GET/PATCH /api/profile` | `GET/PUT /api/settings/analyzer` (+ `/api/webhook`, `/api/debug`) |
| Хранение | колонки `users.*` | `analyzer_config`, `webhook_config` |
| Содержимое | Telegram-бот и chat_id, `notify_events`, email, шаблон назначения платежа (`sber_purpose_template`) | модели и режим распознавания, ключ Anthropic, тумблеры автоотправки, ключ DaData |

Из этого следуют два требования:

1. Всё, что читается из профиля, обязано читаться из профиля **владельца накладной**, а не первого пользователя. Именно поэтому `invoices.ts:1691` (шаблон назначения платежа) — дефект: платёжка компании Б получает шаблон компании А.
2. Платформенные тумблеры (в т.ч. `auto_send_sber`) остаются глобальными **по замыслу** и переносу в настройки компании не подлежат. Безопасность обеспечивается не разделением тумблера, а тем, что само действие выполняется в контексте владельца: после этапа 2 у компании без собственного подключения к Сберу просто нет токена, и автоотправка для неё не срабатывает.

## 6. Этап 1 — уведомления и фоновые актёры

Без изменений схемы. Закрывает подтверждённую утечку уведомлений и опасный автоплатёж.

**6.1. Получатель уведомления — владелец накладной.** `emit()` и так загружает накладную. Порядок меняется: сначала загрузка накладной, затем определение получателя как `invoice.owner_user_id`, затем проверки конфигурации и лимитов.

Точная формулировка правила (уточнена при реализации, см. ниже): накладная, **у которой есть владелец, никогда не адресуется никому другому** — это и был канал утечки. Накладная **без** владельца не принадлежит ни одной компании, поэтому для неё сохраняется откат: сначала `triggeredByUserId`, затем администратор платформы.

> **Уточнение по итогам реализации.** Первая редакция требовала владельца безусловно и при его отсутствии молчала. Прогон существующего набора `tests/notifications/elevated-prices.test.ts` показал, что это ломает боевой сценарий: файл, положенный прямо в `inbox/`, создаётся watcher'ом без пользовательского контекста и получает `owner_user_id = NULL`, то есть уведомления по нему пропали бы полностью. Откат для «ничьих» накладных кросс-тенантной доставкой не является — претендента на такую накладную нет.

**6.2. `notifySupplierExtractError`** не привязан к накладной, поэтому владелец передаётся явным параметром от вызывающей стороны.

**6.3. Фоновые актёры** (`autoSendSber`, диспетчер, шаблон назначения платежа) берут владельца из накладной, а не из `firstUserId()`. Шаблон назначения платежа — профильное, то есть индивидуальное поле (см. 4.1), поэтому читается из профиля владельца накладной.

**6.4. `firstUserId()`** после этого остаётся только для первичного бутстрапа (создание первого админа при пустой базе). Все прочие вызовы удаляются, чтобы паттерн не воспроизвели заново.

**6.5. Автоплатёж.** До завершения этапа 2 `sber_tokens` остаётся общей строкой, поэтому автоотправка в Сбер должна быть запрещена для любой компании, кроме владельца подключения. Проверка добавляется в `autoSendSber` и в диспетчер.

## 7. Этап 2 — изоляция справочников

**7.1. Схема.** Все миграции идемпотентные, с `detect()` (правило 16 CLAUDE.md), DDL в MySQL нетранзакционен — каждая должна переигрываться после частичного отказа.

**Ключевой принцип — Вариант A** из спеки по поставщикам, принимается для всех таблиц: не переделываем первичный ключ в составной, а добавляем нullable `owner_user_id`, бэкфиллим и вешаем `UNIQUE(owner_user_id, <естественный ключ>)`. Там, где сейчас естественный ключ является PK (`suppliers.inn`, `onec_nomenclature.guid`, `nomenclature_price_stats.onec_guid`), вводится суррогатный `id INT AUTO_INCREMENT PRIMARY KEY`.

Обоснование (из принятого ранее решения): совпадает с остальной схемой, где везде суррогатный `id`; цель для будущих внешних ключей остаётся стабильной; добавление колонки и уникального индекса — заметно более лёгкий DDL, чем перестройка PK на заполненной таблице. Составной PK был рассмотрен и **отклонён**: он требует `owner_user_id NOT NULL`, что убирает признак «системная строка, владелец неизвестен», допустимый для накладных.

| Таблица | Изменение |
|---|---|
| `suppliers` | + `owner_user_id`, суррогатный `id` PK, `UNIQUE(owner_user_id, inn)` |
| `onec_nomenclature` | + `owner_user_id`, суррогатный `id` PK, `UNIQUE(owner_user_id, guid)` |
| `nomenclature_mappings` | + `owner_user_id`, UNIQUE `scanned_name` → `UNIQUE(owner_user_id, scanned_name)` |
| `nomenclature_price_stats` | + `owner_user_id`, суррогатный `id` PK, `UNIQUE(owner_user_id, onec_guid)` |
| `supplier_nomenclature_mappings` | + `owner_user_id`, правка UNIQUE |
| `sber_tokens` | снять `CHECK (id = 1)`, `UNIQUE(owner_user_id)` |

Оговорка по `NULL` в MySQL: `UNIQUE` не схлопывает `NULL`, поэтому легаси-строки бэкфиллятся конкретным id админской компании, а не остаются `NULL` — иначе теряется защита от дублей.

**7.2. Бэкфилл.** Все существующие строки получают `owner_user_id` первой (админской) компании — исторически эти данные принадлежат ей. Новая компания стартует с пустыми справочниками и подключает свои 1С и Сбер самостоятельно.

**7.3. Репозитории.** `supplierRepo`, `onecNomenclatureRepo`, `mappingRepo`, `sberTokenRepo`, репозиторий price-stats — каждый метод принимает владельца. Владелец не имеет значения по умолчанию: отсутствие параметра должно быть ошибкой типов, а не тихим чтением всех арендаторов.

**7.4. Кэш маппера.** `NomenclatureMapper` переводится на кэш, ключованный владельцем (`Map<ownerUserId, CatalogIndex>`), `invalidateCache(owner)` сбрасывает только своего. Без этого правка SQL не даёт изоляции.

**7.5. Источники владельца вне HTTP-контекста.** `fileWatcher` берёт владельца из накладной (он уже проставляется при загрузке из `meta.ownerUserId`); обмен с 1С — из `onec_connections.owner_user_id`.

**7.6. Снятие флага.** `config.dataScopingEnabled` удаляется, все ветки `if (!config.dataScopingEnabled || role === 'admin')` схлопываются в безусловную проверку владельца.

## 8. Риски

| Риск | Смягчение |
|---|---|
| Смена PK на заполненных таблицах — тяжёлый и нетранзакционный DDL | дамп БД перед выкаткой; каждая миграция идемпотентна и переигрывается |
| Пропущенный вызов репозитория без владельца тихо вернёт чужие данные | владелец — обязательный параметр, без значения по умолчанию; проверка `tsc --noEmit` ловит пропуски на этапе компиляции |
| Кэш маппера переживает запрос и живёт в процессе | ключевание по владельцу, отдельная проверка в тестах |
| После снятия admin-bypass админ может потерять доступ к своим рабочим экранам | админ остаётся владельцем своей компании; платформенные настройки закрыты `requireAdmin` и не скоупятся |
| Автоплатёж со счёта чужой компании до завершения этапа 2 | запрет в этапе 1 (п. 6.5) |

## 9. Тестирование

Тесты только на `127.0.0.1` с базой, содержащей `test` в имени (правило 17 CLAUDE.md) — гард в `tests/helpers/db.ts` не отключать.

- Две компании в фикстуре; для каждой таблицы из п. 5 проверяется, что компания Б не видит строк компании А (список, чтение по ключу, обновление, удаление).
- Уведомления: событие по накладной компании Б адресуется владельцу Б, а не первому пользователю.
- Маппер: после прогрева каталога компанией А запрос компании Б не получает её позиций.
- Сбер: попытка отправки платежа при подключении, принадлежащем другой компании, отклоняется.
- Совпадающие ключи: один и тот же ИНН поставщика и один и тот же `scanned_name` у двух компаний сосуществуют независимо.

## 10. Вне области

- Несколько сотрудников на одну компанию (потребует таблицу `companies`) — сознательно отложено, выбрана модель «аккаунт = компания».
- Отдельная роль поддержки со сквозным доступом.
- Перенос платформенных тумблеров (`auto_send_sber` и т.п.) в настройки компании — **не планируется**: по 4.1 они глобальны по замыслу.
- Самостоятельная регистрация компаний и биллинг.
