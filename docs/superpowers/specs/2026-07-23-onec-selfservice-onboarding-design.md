# Дизайн: самообслуживаемое подключение 1С-баз к аккаунтам ScanFlow (пейринг-код)

- Дата: 2026-07-23
- Статус: утверждён (brainstorming), готов к плану реализации
- Ветка: `feat/1c-selfservice-onboarding`
- Связано: `onec_connections` / `onecConnectionRepo` / `src/api/routes/onec.ts`, обработка `1c/КНД_ЗагрузкаНакладныхСканер/`

## Контекст: что УЖЕ есть (переиспользуем как есть)

При проектировании выяснилось, что scoped-инфраструктура для 1С уже реализована:

- **`onec_connections`** — таблица scoped-токенов подключений: `owner_user_id`, `name`, `token_hash`, `token_prefix`, `active`, `last_used_at`, `last_ip`, `created_at`, `revoked_at` (FK на `users`, `ON DELETE CASCADE`).
- **`onecConnectionRepo`** — `create(ownerUserId, name) → { connection, token }` (токен показывается один раз), `authenticate(token, ip)`, `revoke(id, ownerUserId)`, `list(ownerUserId)`.
- **Обмен `/api/onec/exchange/*`** — роутер под `onecTokenAuth` (заголовок `X-1C-Token`), ставит `req.onecConnection`; все данные скоупятся по `owner_user_id` подключения. Роуты: `status`, `invoices/pending`, `invoices/:id`, `invoices/:id/photos[/:file]`, `invoices/:id/status`, `nomenclature/*`.
- **Обработка 1С уже работает через этот токен** — шлёт `X-1C-Token: КОНСТ_КлючAPI()` на `/api/onec/exchange/*`. Токен хранится в `ХранилищеОбщихНастроек` базы; сохраняется процедурой `СохранитьТокенПодключения`.
- **Кабинет** (`operations.js` + `onecAdminRouter`): создать подключение → показ токена, список баз, отзыв, `/setup`-инструкция, отдача исходников обработки (`/api/onec/source/:part`).

**Ничего из перечисленного не трогаем.**

## Проблема (реальный gap)

1. Создание подключения сейчас **только у админа** (`/api/onec` под `apiKeyAuth + requireAdmin`; в UI для роли `user` — «Подключения 1С настраивает администратор»). То есть это НЕ самообслуживание.
2. Даже когда подключение создано, клиент получает **длинный токен** (48-символьный hex) и должен вставить его в обработку — на масштабе это ошибки/утечки.

## Цель

Клиент (роль `user`) **сам** из своего кабинета получает **короткий одноразовый код**, вводит его в обработке, и база подключается — без длинного токена и без участия админа. Одна `.epf` на всех.

## Решения (brainstorming)

- Онбординг: **самообслуживание клиентом**; среда 1С: **on-prem**; механизм: **пейринг-код**.
- Код генерит **сам клиент** (роль `user`), не админ.
- Токен подключения — существующий `onec_connections` (scoped, отзываемый). Пейринг-код лишь заменяет ручное копирование токена.

## Общий поток

```
Кабинет клиента (роль user):  «Подключить 1С» → POST /api/onec/pairing-code → короткий код  1C-4F7K-9Q2R  (TTL ~15 мин)
Обработка в 1С:               поле «Код подключения» → «Подключить»
                               → POST /api/onec/pair {code}  (публичный)
                               → сервер: redeem кода → onecConnectionRepo.create(owner, base_name) → { token, exchange_url }
                               → обработка: СохранитьТокенПодключения(token)
Дальше:                       существующий обмен /api/onec/exchange/* по X-1C-Token
```

## Компоненты (что дорабатываем)

### 1. Данные — новая миграция

`onec_pairing_codes`:
- `id`, `code` (короткий, формат `1C-XXXX-XXXX`, UNIQUE), `owner_user_id` (FK users, CASCADE), `base_name` (VARCHAR, имя базы/метка для будущего подключения; можно пустое), `created_at`, `expires_at`, `used_at` (NULL пока не использован).
- Индекс по `code`; по `owner_user_id`.
- Номер: следующий после текущего максимума (на момент дизайна max = **55**, значит **56**; план перепроверяет фактический max). Идемпотентна (`CREATE TABLE IF NOT EXISTS`).

### 2. Репозиторий `onecPairingRepo`

- `create(ownerUserId, baseName): Promise<{ code, expiresAt }>` — инвалидирует прошлые неиспользованные коды этого пользователя (`used_at = NOW()` или удаление), генерит новый короткий код, TTL ~15 мин.
- `redeem(code): Promise<{ ownerUserId, baseName } | null>` — атомарно: код существует, не использован, не истёк → помечает `used_at`, возвращает владельца; иначе null.
- Генерация кода: короткий, из безопасного алфавита (как `generatePassword`, без похожих символов), с префиксом `1C-`.

### 3. Роуты (в `src/api/routes/onec.ts` + монтирование в `server.ts`)

- **`POST /api/onec/pairing-code`** — доступен **любому авторизованному** (роль `user` тоже), НЕ под `requireAdmin`. Body: `{ base_name?: string }`. Создаёт код для `req.user.id`, возвращает `{ code, expires_at }`.
  - Монтирование: отдельный `onecUserRouter` под `apiKeyAuth` (без `requireAdmin`), примонтирован на `/api/onec` **до** админского роутера (Express матчит по порядку; user-роутер обрабатывает `/pairing-code`, админский — остальное). Либо явный `app.post('/api/onec/pairing-code', apiKeyAuth, …)` до `app.use('/api/onec', apiKeyAuth, requireAdmin, onecAdminRouter)`.
- **`POST /api/onec/pair`** — **публичный** (до токена/ключа), строгий rate-limit. Body: `{ code }`. `redeem(code)` → при успехе `onecConnectionRepo.create(ownerUserId, baseName || 'Подключение 1С')` → `{ token, exchange_url, header: 'X-1C-Token' }`. Иначе `400 { error: 'code_invalid_or_expired' }`.
  - Монтирование: `app.post('/api/onec/pair', pairLimiter, …)` до `app.use('/api/onec', apiKeyAuth, requireAdmin, …)`, чтобы не попасть под admin-guard.
- (Опц., v2) `GET /api/onec/version` — публичный — актуальная версия `.epf` + ссылка на скачивание для само-обновления обработки.

### 4. Кабинет (frontend, `operations.js`)

- Клиентский виджет «Подключить 1С» (виден роли `user`, сейчас там «настраивает администратор»): кнопка «Получить код» → `POST /onec/pairing-code` → показывает код крупно + короткую инструкцию «введите код в обработке 1С, поле „Код подключения“» + таймер/TTL.
- Существующий админский блок подключений (список/отзыв/токен) — не трогаем.

### 5. Обработка 1С (`ObjectModule.bsl` + форма)

- Форма: новое поле **«Код подключения»** + кнопка **«Подключить»**. Существующее поле «сырой токен» оставить как ручной fallback.
- `Процедура ПодключитьПоКоду`: `POST https://scanflow.ru/api/onec/pair {code}` → при успехе `СохранитьТокенПодключения(token)` + сообщение «Подключено». При ошибке — «Код неверен или истёк, сгенерируйте новый в кабинете».
- «Проверить соединение» — существующая логика (`GET /api/onec/exchange/status`).
- `.epf` пересобрать вручную из `ObjectModule.bsl`/формы (автодеплой не касается).

## Безопасность

- Код короткий, **одноразовый**, TTL ~15 мин, привязан к `user`; всё по HTTPS.
- `POST /api/onec/pair` — жёсткий rate-limit (перебор кодов); алфавит/длина кода такие, что перебор в окне TTL непрактичен.
- Токен — существующий scoped `onec_connections` (только обмен, отзыв независим от основного ключа). `/pair` не логирует токен.

## Обработка ошибок

- Код истёк/использован/неверен → `400 code_invalid_or_expired` → в обработке понятное сообщение.
- Токен отозван (позже) → `401` на обмене → «Подключитесь заново».
- Сеть/SSL → обработка показывает ошибку соединения (как сейчас).

## Тестирование (vitest, тест-БД)

- `onecPairingRepo.create`: TTL, инвалидация прошлых кодов, привязка к user.
- `redeem`: валидный код → владелец + `used_at`; повторный тот же → null; истёкший → null; неизвестный → null.
- `POST /api/onec/pairing-code`: роль `user` получает код (не 403); роль admin тоже.
- `POST /api/onec/pair`: валидный код → создаёт `onec_connection` нужного владельца + возвращает токен; невалидный → 400; повтор того же кода → 400.
- Изоляция end-to-end: токеном, полученным по коду клиента, `/api/onec/exchange/invoices/pending` возвращает только накладные этого владельца.
- 1С BSL — вручную (обработка компилируется в `.epf` отдельно).

## Порядок реализации (для плана)

1. Миграция `onec_pairing_codes` (перепроверить актуальный max) + `onecPairingRepo` + тесты репозитория.
2. `POST /api/onec/pairing-code` (user-auth) + монтирование + тест доступа роли `user`.
3. `POST /api/onec/pair` (public + rate-limit) → создаёт connection через существующий репозиторий + тесты (валид/невалид/повтор/изоляция).
4. Кабинет: клиентский виджет «Подключить 1С» с показом кода.
5. Обработка 1С: поле «Код подключения» + `ПодключитьПоКоду`; ручная сборка `.epf`.
6. (v2, опц.) `GET /api/onec/version` + само-обновление обработки.

## Не-цели

- 1С:Фреш/облако; мультитенантный Сбер; переизоляция исторических данных.
- Изменения в `onec_connections` / `onecConnectionRepo` / обмене / изоляции — переиспользуем как есть.
