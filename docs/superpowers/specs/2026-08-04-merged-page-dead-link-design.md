# Битая ссылка из бота после склейки страниц — разбор и починка

- **Дата:** 2026-08-04
- **Статус:** согласован, к реализации
- **Повод:** PF-задача `3b2b594c` «Дебаг ошибок накладных в боте». Симптомы от 16.07: в бот пришло уведомление о накладной №654, ссылка `scanflow.ru/#/invoices/654` не открывается, на сайте накладной нет. Соседние 653 и 655 на месте. Лога об ошибке не поступало, и непонятно, загрузилось ли фото и надо ли переснимать.

## 1. Что произошло на самом деле

Ошибки не было. Это **штатная склейка многостраничной накладной**, у которой наружу торчат последствия.

Последовательность в `fileWatcher.processFile()`:

1. Строка накладной создаётся, и **сразу** — до всякого OCR — уходит уведомление
   `photo_uploaded` со ссылкой `/#/invoices/<id>` ([fileWatcher.ts:680](../../../src/watcher/fileWatcher.ts#L680)).
   Именно поэтому в пузыре пустые «Поставщик: —» и «Сумма: —»: распознавать ещё нечего.
2. Отрабатывает OCR, страница опознаётся как продолжение уже существующей накладной.
3. Ветка склейки **удаляет временную строку**: `await invoiceRepo.delete(invoice.id)`
   ([fileWatcher.ts:993](../../../src/watcher/fileWatcher.ts#L993)). Удаление намеренно раннее — чтобы склейка была атомарной и не оставляла сирот при падении в середине 10–60-секундного вызова Claude.
4. Позиции и файл страницы уже вошли в родительскую накладную (её `file_name` становится списком через запятую).

Итог: в чате висит пузырь «Накладная №654 · Загружена» с мёртвой ссылкой, а строки 654 больше нет. Открытие ссылки даёт «Накладная не найдена» и редирект в список ([invoices.js:741](../../../public/js/invoices.js#L741)).

**Почему не было лога об ошибке.** Потому что ошибки и не было — это путь успеха. Лог склейки пишет только id накладной-приёмника (`id: targetInvoiceId`), id удалённой страницы не попадает в лог вообще. То есть по логам невозможно установить, что 654 стала частью 653 — ровно это и мешало разобраться.

**Фотографировать заново не нужно** — страница уже в родительской накладной. Это главный практический вывод для команды.

Путь удаления в конвейере ровно один: дубликаты строку не удаляют, а помечают флагом (`markAsDuplicate`), crash recovery с 14.07 тоже не удаляет (правило 21 в CLAUDE.md).

## 2. Что чиним

Три отдельные проблемы, у каждой свой фикс.

### 2.1 Ссылка должна работать (миграция 60 + резолв)

Заводим таблицу связей:

```sql
CREATE TABLE invoice_merges (
  source_id  INT NOT NULL PRIMARY KEY,   -- id удалённой страницы
  target_id  INT NOT NULL,               -- в какую накладную вошла
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_invoice_merges_target (target_id),
  CONSTRAINT fk_merges_target FOREIGN KEY (target_id) REFERENCES invoices(id) ON DELETE CASCADE
)
```

FK только на `target_id`: `source_id` — идентификатор уже удалённой строки, ссылаться не на что. `ON DELETE CASCADE` — если приёмник потом удалят, связь бессмысленна.

Запись делается **до** `invoiceRepo.delete()` в обеих ветках склейки (через объединённый OCR-текст и append-fallback).

`GET /api/invoices/:id`: накладной нет → ищем в `invoice_merges` → отвечаем `404` с телом `{ error, merged_into: 653 }`. Фронт вместо «Накладная не найдена» переходит на накладную-приёмник и показывает: «Эта страница вошла в накладную #653 — переключились на неё».

Цепочки склеек (страница вошла в накладную, которую потом склеили с третьей) резолвим по ссылкам, но не больше 5 шагов — защита от петли, если данные окажутся кривыми.

### 2.2 Пузырь в чате не должен оставаться мёртвым

После успешной склейки редактируем пузырь удалённой страницы: «Страница вошла в накладную #653» со ссылкой на приёмник.

Порядок важен: пары `(chat_id, message_id)` лежат в `invoice_telegram_messages` с `ON DELETE CASCADE`, поэтому их надо **прочитать до** удаления строки, а редактировать уже после успешной склейки.

Если чат недоступен — просто логируем. Уведомления не имеют права ломать конвейер (правило 9).

### 2.3 Видимость в логах

В лог склейки добавляем `sourceInvoiceId` — оба id рядом. Без этого связь «654 → 653» не восстанавливается ни по логам, ни по базе.

Отдельной строкой логируем сам факт: `Page merged into parent invoice { sourceId, targetId, ownerUserId }` — на уровне `info`, до удаления.

## 3. Чего сознательно НЕ делаем

**Не переносим отправку `photo_uploaded` на «после OCR».** Уведомление «фото загружено» существует, чтобы человек сразу видел: снимок дошёл до сервера. Если ждать OCR (до 2–3 минут), оно потеряет смысл, а при падении OCR не придёт вовсе.

**Не отменяем раннее удаление строки.** Оно защищает от сирот в статусе `parsing` при падении посреди склейки — это осознанное решение с историей. Мы лечим следствие (мёртвая ссылка), а не убираем защиту.

## 4. Что проверяем

- миграция 60 идемпотентна;
- склейка пишет связь до удаления, оба id есть в логе;
- `GET` удалённой страницы отдаёт `merged_into`, фронт переключается на приёмник с понятным сообщением;
- цепочка склеек резолвится до конечной накладной, петля не вешает запрос;
- пузырь в Telegram переписывается на «страница вошла в накладную #N»;
- недоступный чат не ломает склейку.
