# Корректность склейки многостраничных накладных — design

- **Дата:** 2026-07-23
- **Статус:** согласован, готов к плану реализации
- **Повод:** инцидент — две разные накладные ООО «ОМЕГА ПРИНТ» (№287 и №288), загруженные подряд, слились в одну запись; данные №288 (этикетка-пустышка, 9000 ₽) молча потеряны.

## 1. Что происходит сейчас

Загрузка идёт в один из двух путей в зависимости от `analyzer_config.mode`:
- **watcher** (`src/watcher/fileWatcher.ts`, режим `claude_api` — текущий на проде): пять эвристик мерджа A/B/B2/C/D;
- **dispatcher** (`src/api/routes/dispatcher.ts`, режим `dispatcher`): `findMultiPageTarget` (A/C/D) + `reconcileMultiPage`.

Обе стратегии при обнаружении «страницы существующей накладной» делают одно и то же (watcher ~918-990, dispatcher ~275-362):
1. приклеивают файл и OCR-текст новой страницы к существующей;
2. **удаляют строку новой страницы** (`invoiceRepo.delete`);
3. отдают Claude **склеенный текст обеих страниц** как одну многостраничную (`analyzeMultiPageText`);
4. перезаписывают поля существующей накладной результатом unified-разбора.

## 2. Корневая причина (две наложившиеся)

**2.1. Триггер сработал ложно.** Номерная эвристика (`invoiceRepo.findRecentByNumber`) корректно отвергает 287 vs 288: нормализованные номера и цифросеквенции различаются. Но **Strategy B2 «row_no continuation»** (`fileWatcher.ts:807-871`) матчит по *поставщику + 5-минутному окну* и близости `row_no`, **не проверяя, что у обеих накладных есть разные номера**. Две разные накладные одного поставщика, загруженные подряд, для неё выглядят как «хвост и голова одной».

**2.2. Combined re-analysis молча теряет данные.** Тексты №288 (пустышка) и №287 (Круасаны/Формы) склеены через `--- СТРАНИЦА ---` и отданы Claude как одна накладная. Claude свёл к №287, №288 исчезла. Проверки, что unified-результат не потерял позиции/сумму, нет.

**Нарушенный инвариант:** если у обеих накладных есть номер и они различаются — это заведомо разные документы, мёржить нельзя никогда, какой бы эвристике это ни казалось продолжением.

## 3. Принятые решения

| Вопрос | Решение |
|---|---|
| Философия | **Страховка с двух сторон**: консервативный триггер + пост-проверка после склейки + авто-откат без потери данных. |
| Типы настоящих многостраничных | Бывают **разные** — и с номером на каждом листе, и с номером только на первом. Эвристику продолжения (страница без номера) выбрасывать нельзя. |
| Подход | Не переписывать эвристики, а накрыть их защитой (вариант A из брейнсторма). Полный рефактор в «контейнер страниц» (вариант C) отклонён как YAGNI. |

## 4. Дизайн

### 4.1. Единый предохранитель `canMerge` (Секция 1)

Новый модуль `src/services/mergeDecision.ts` с чистой функцией:

```
mergeBlockedByNumber(a: { invoice_number }, b: { invoice_number }): boolean
```

Правило: возвращает `true` (мердж запрещён), если у **обеих** сторон номер непустой и `normalizeInvoiceNumber(a) !== normalizeInvoiceNumber(b)`. Во всех остальных случаях (у одной номера нет, номера совпадают) — `false`.

Вызывается во **всех** точках, где выбран кандидат на мердж, **до** любых мутаций:
- watcher: сразу после того, как `existingInvoice` определён (перед `fileWatcher.ts:918`);
- dispatcher: внутри `findMultiPageTarget` для веток C/D и в `reconcileMultiPage` перед склейкой сиблингов.

Ветка A (`findRecentByNumber`) уже отвергает разные номера, но предохранитель применяется и к её результату — единая точка истины, дешевле перепроверить, чем полагаться на внутреннюю логику каждой эвристики.

Как накрываются все случаи:
- многостраничная, номер на каждом листе → номера совпадают → `false` → сливаем;
- многостраничная, номер только на первом → у продолжения номера нет → `false` → эвристика продолжения (row_no) сливает;
- две разные накладные (287/288) → номера есть и разные → `true` → **блок**.

**Приоритет: номер сильнее row_no.** Предохранитель абсолютен. Если у обеих есть номер и он разный — блок, **даже если позиции формально продолжаются по row_no**. В инциденте 287/288 их `row_no` случайно подошли под «продолжение», но разные номера теперь дают жёсткий стоп.

Пример «продолжения без номера» (штатный мердж): накладная A с №123 и позициями row_no 1-5; следом страница B без номера с позициями row_no 6,7,8. У B номера нет → предохранитель не блокирует → B2 видит gap = 6 − (5+1) = 0 → сливаем в одну накладную с позициями 1-8; пост-проверка: 8 позиций ≥ 5+3 → потери нет.

Причина вынести в модуль: логика решения сейчас продублирована в watcher и dispatcher; общий модуль не даёт копиям разъехаться и даёт одну точку для юнит-тестов.

### 4.2. Пост-проверка unified-результата (Секция 2)

Новая чистая функция там же:

```
mergeLostData(before: { itemCount, totalSum }[], after: { itemCount, totalSum }): boolean
```

После combined re-analysis, **до** фиксации, сравнить unified-результат с исходными страницами. Потеря данных = слияние проглотило содержимое:
- позиций в unified **меньше**, чем суммарно было на склеиваемых страницах, **или**
- unified `total_sum` **меньше** максимальной из исходных сумм страниц (для настоящей многостраничной grand-total ≥ суммы любой отдельной страницы; для двух разных документов эта проверка ловит проглоченный).

Если `true` — **откат** (см. 4.3): не мёржим, оставляем обе накладные раздельно, помечаем как возможные сиблинги (существующий баннер «Похоже на ту же накладную — Объединить?»).

Это второй рубеж на случай, когда предохранитель пропустил (обе страницы без номера — настоящее продолжение), а Claude всё равно потерял строку.

### 4.3. Отложенное удаление вместо раннего (Секция 3)

Сейчас строка новой страницы удаляется (`invoiceRepo.delete`) **до** re-analysis — ради атомарности, но для отката это фатально: восстанавливать нечего.

Новый порядок:
1. combined re-analysis → unified-результат;
2. пост-проверка `mergeLostData`;
3. **только при успехе** — в транзакции: перенести позиции/файлы на каноническую, обновить поля, удалить строку страницы;
4. при провале проверки — ничего не удалять, обе накладные живут, пометить сиблингами.

Цена размена: если процесс упадёт **между** append и фиксацией — останутся **две** строки (дубль-страница), а не потеря. Это ровно консервативный выбор из решения: краш → лишняя строка (правится вручную кнопкой «Объединить»), не пропажа.

Замечание про раннее удаление: комментарий в коде (`fileWatcher.ts:952-959`) обосновывает ранний delete защитой от orphan-строки в статусе `parsing` при краше. Этот риск переносится в противоположную сторону (дубль вместо orphan) и остаётся видимым/чинибельным; потеря данных — нет. Размен осознанный.

### 4.4. Область применения

Оба пути (watcher и dispatcher) переводятся на общий `mergeDecision`. `reconcileMultiPage` в диспетчере (`dispatcher.ts:317-362`), матчащий сиблингов по supplier+number, получает тот же предохранитель. Ручная склейка (`POST /api/invoices/:id/merge-into/:targetId`) предохранителем **не** ограничивается — это осознанное действие пользователя.

## 5. Тестирование

Правило 17 CLAUDE.md: тесты только на `127.0.0.1`, `DB_NAME` с `test`, гард в `tests/helpers/db.ts` не отключать.

Юнит (чистые функции, без БД):
- `mergeBlockedByNumber`: разные номера → true; совпадающие → false; один пустой → false; оба пустых → false; нормализация («№ 287 » vs «287»).
- `mergeLostData`: unified потерял позицию → true; unified потерял сумму → true; корректная многостраничная (все позиции на месте) → false.

Интеграционные (реальная тестовая БД, стиль соседних `tests/watcher`, `tests/database`):
1. **Регресс 287/288**: две разные накладные одного поставщика подряд → **две** записи, не слиты, помечены сиблингами.
2. Настоящая многостраничная, один номер на страницах → **одна** запись, все позиции.
3. Продолжение без номера на второй странице → **одна** запись, все позиции.
4. Combined re-analysis потерял позицию → откат, обе накладные целы.
5. Симуляция краша после append (до фиксации) → обе строки живы, ни одна не потеряна.

## 6. Риски

| Риск | Смягчение |
|---|---|
| Настоящая многостраничная с разными номерами на листах (редко, но бывает у некоторых поставщиков) | Предохранитель заблокирует авто-мердж → пользователь склеит вручную (кнопка есть). Консервативно: лишняя ручная операция, не потеря. |
| Пост-проверка ложно сработает на корректной многостраничной (unified законно переоформил позиции) | Порог по позициям — «меньше суммы страниц», не «не равно»; grand-total ≥ максимума. Ложный откат → две записи + баннер, данные целы. |
| Отложенное удаление оставляет дубль при краше | Дубль виден в списке и чинится кнопкой «Объединить»; дедуп по `file_hash`/имени не даёт повторной обработки того же файла. |
| Диспетчерский путь и watcher разойдутся | Единый `mergeDecision` — одна реализация на оба; дублирования логики решения больше нет. |

## 7. Вне области

- Полный рефактор модели в «накладная = контейнер страниц» (вариант C).
- Улучшение самого OCR-разбора позиций (напр. инцидент «90 л vs 30 шт» у РПС ОПТ — отдельная тема качества распознавания, не склейки).
- Изменение ручной склейки — остаётся как есть.
