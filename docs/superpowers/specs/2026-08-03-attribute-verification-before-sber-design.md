# Чек-лист проверенных реквизитов перед отправкой платежа в Сбер — design

- **Дата:** 2026-08-03
- **Статус:** согласован, к реализации
- **Повод:** перед каждой отправкой платёжки бухгалтер вручную сверяет с фотографией номер, дату, поставщика, сумму и НДС. Отметить, что уже сверено, негде — легко забыть, на чём остановился, и уйти платить по непроверенным данным. Нужны галочки на этих пяти атрибутах, запрет отправки в Сбер пока не отмечены все, и одна общая галочка рядом с кнопкой отправки, закрывающая сразу все пять.

## 1. Набор атрибутов

Шесть полей шапки накладной, которые сверяют глазами:

| Ключ | Источник значения | Подпись в UI |
|------|-------------------|--------------|
| `number`   | `invoices.invoice_number` | Номер |
| `date`     | `invoices.invoice_date`   | Дата |
| `supplier` | `invoices.supplier`       | Поставщик |
| `total`    | `invoices.total_sum`      | Сумма |
| `vat`      | `invoices.vat_sum`        | В т.ч. НДС |
| `vat_rate` | `invoice_items.vat_rate` (уникальные значения) | Ставка НДС |

**Ставка НДС — отдельный пункт от суммы НДС** (добавлено 2026-08-03 по итогам
обсуждения). Сумма НДС может сойтись с напечатанной в документе и при неверно
распознанной ставке — например 22% вместо 20% на другой налоговой базе, — поэтому
одна общая отметка скрывала бы реальную ошибку.

Ставка хранится по позициям, а не в шапке, поэтому в карточке показываем набор
уникальных ставок: `10%`, `10%, 20%` для смешанной накладной или `—`, если
ставку не распознали. Сверять удобно именно в шапке: в таблице позиций ставка
тонет среди строк. Правкой позиции ставка не меняется (item-PATCH принимает
только количество/единицу/цену/сумму), поэтому её отметку сбрасывает только
полное перераспознавание.

ИНН и расчётный счёт в набор **не входят** — сознательное решение заказчика: чем больше галочек, тем медленнее рутина. Отмечу риск в документации, но поведение не меняю: ошибка OCR в счёте уводит деньги другому лицу, и эти реквизиты остаются на визуальном контроле в блоке «Реквизиты поставщика», без принудительной отметки.

## 2. Модель данных (миграции 57 и 58, аддитивные, идемпотентные)

Колонки в `invoices` через `hasColumn`-guard + `ALTER TABLE ADD COLUMN` — как миграции 55/47, без DROP и без правки существующих:

```
-- 57
attr_checked_number   TINYINT(1) NOT NULL DEFAULT 0
attr_checked_date     TINYINT(1) NOT NULL DEFAULT 0
attr_checked_supplier TINYINT(1) NOT NULL DEFAULT 0
attr_checked_total    TINYINT(1) NOT NULL DEFAULT 0
attr_checked_vat      TINYINT(1) NOT NULL DEFAULT 0
-- 58
attr_checked_vat_rate TINYINT(1) NOT NULL DEFAULT 0
```

Ставка вынесена в отдельную миграцию 58, а не дописана в 57, потому что 57 к
моменту решения уже применилась на dev-базе: `runMigrations()` сверяется только
с номером версии, поэтому дописанная колонка на dev не появилась бы никогда
(правило 16 в CLAUDE.md).

Отдельные колонки, а не JSON: по ним нужен серверный предикат «все пять» в двух местах отправки, и в будущем — фильтр/статистика по непроверенным.

**Бэкфилл не делаем.** Все существующие накладные стартуют непроверенными (`0`). Это осознанно: обратное означало бы объявить проверенным то, что никто не сверял, а вся ценность фичи в честности отметки. Практическое следствие — накладные, по которым платёж ещё не создан, потребуют одного клика по общей галочке. Уже оплаченные накладные это не затрагивает: гейт стоит только на создании нового платежа.

**Кто и когда отметил — не храним.** Аудит потребовал бы отдельную таблицу; сейчас задача — не забыть, а не расследовать. Если понадобится, `integration_events` уже есть и расширяется отдельно.

## 3. Сброс отметок при изменении данных

Отметка означает «я сверил ЭТО значение с фотографией». Как только значение меняется, отметка становится ложью, поэтому:

- **`PATCH /api/invoices/:id`** — правка поля сбрасывает галочку **только этого** поля (правка `total_sum` → `attr_checked_total = 0`). Сброс делается в той же транзакции, что и сам update. Правка поля вне пятёрки (например `supplier_inn`) галочек не трогает.
- **Полное перераспознавание** — «Пересканировать фото», «LLM: переделать всё», добавление страницы, склейка многостраничной — сбрасывает **все пять**, потому что переписывает всю шапку.
- Сброс идемпотентен: снимать уже снятую галочку безопасно.

## 4. API

**`POST /api/invoices/:id/attr-check`**, тело `{ attr: 'number'|'date'|'supplier'|'total'|'vat'|'all', value: boolean }`.

- owner-scoped (`invoice.owner_user_id !== req.user.id` → 404, как в остальных ручках накладной), доступен любому пользователю аккаунта — это рабочая операция, не админская;
- `attr: 'all'` ставит/снимает сразу пять — за ним стоит общая галочка у кнопки отправки;
- ключ атрибута валидируется по белому списку и отображается в имя колонки через фиксированный маппинг, **никакой интерполяции из тела запроса** (правило 18 в CLAUDE.md);
- отвечает актуальным состоянием всех пяти флагов + `all_checked: boolean`, чтобы фронт не догадывался, а перерисовывался по ответу сервера.

`GET /api/invoices/:id` отдаёт пять флагов в составе накладной (они уже попадают в `SELECT *`).

## 5. Запрет отправки в Сбер

Предикат один на оба пути отправки — общая функция `assertAttributesChecked(invoice)` в роуте:

- **`POST /api/invoices/:id/send-sber`** — при неполном чек-листе `409` с телом `{ error, attrs_unchecked: ['total','vat'] }`. Код 409, а не 400: запрос корректен, но состояние объекта не позволяет операцию — тем же кодом уже отвечает лимит согласования и «платёж уже создан».
- **`POST /api/invoices/send-sber-batch`** → `bulkSendSber()` — накладные с неполным чек-листом не отправляются, а попадают в отчёт пачки как ошибка с понятным текстом. Остальные из пачки уходят как обычно: частичный успех для массовой операции здесь уже норма.

Проверка стоит **до** создания платежа и до обращения к API Сбера, рядом с существующими проверками (`total_sum > 0`, `supplier_inn`, лимит согласования).

Гейт **не распространяется** на отправку в 1С: там документ можно поправить и перепровести, деньги не двигаются. Заказчик просил именно про Сбер.

## 6. UI

**Карточка накладной.** У пяти полей шапки появляется чекбокс слева от подписи. Отмеченное поле получает приглушённую зелёную галочку и подпись-title «Сверено с фото». Остальные поля шапки (Статус, Обработка, Файл, Создан) чекбоксов не получают — их не сверяют.

**Рядом с кнопкой «Отправить в Сбербанк»** — чекбокс «Все реквизиты сверены»:
- отмечен ⇔ отмечены все пять (состояние вычисляется от них, отдельного флага в БД нет — иначе появился бы источник рассинхрона);
- клик по нему ставит/снимает все пять разом (`attr: 'all'`);
- пока не отмечен, кнопка отправки **disabled** с подсказкой, каких именно полей не хватает.

Блокировка кнопки — удобство, а не защита: настоящий запрет живёт на сервере (п. 5), потому что кнопку можно обойти запросом напрямую.

**Список накладных.** Ничего не меняем: колонок и так десять, а чек-лист — операция карточки.

## 7. Что проверяем

- миграция 57 идемпотентна: повторный прогон на применённой базе не падает;
- `attr-check` с чужой накладной → 404; с мусорным `attr` → 400;
- отправка в Сбер при неполном чек-листе → 409 и платёж не создан (`sber_payments` пуст);
- отправка при полном чек-листе доходит до обычной логики;
- массовая отправка: непроверенные попадают в отчёт как ошибки, проверенные уходят;
- правка `total_sum` через PATCH снимает только `attr_checked_total`;
- перераспознавание снимает все пять;
- общая галочка ставит и снимает все пять, кнопка отправки блокируется и разблокируется без перезагрузки страницы.
