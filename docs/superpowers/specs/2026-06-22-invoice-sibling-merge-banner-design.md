# Баннер «похоже на ту же накладную» + ручная склейка дублей-страниц

**Дата:** 2026-06-22
**Статус:** утверждён к реализации

## Проблема

Камера грузит страницы многостраничной накладной обычным путём
(`/api/upload` → watcher → `processFile`). Автосклейка по номеру
(Strategy A, `fileWatcher.ts` → `invoiceRepo.findRecentByNumber`) подхватывает
страницу к существующей накладной только если та:

1. создана **в последние 10 минут**, и
2. в статусе `processed / parsing / ocr_processing` (не `approved`/`sent`).

Если страница приходит позже окна или после отправки накладной в 1С, она
оформляется **отдельной накладной**. Воспроизведение: накладная `17-0348232`
(ООО «Свит Лайф Фудсервис», 09.06.2026) лежит как две записи #151 и #159, обе
«Отправлен». Ручной склейки в UI нет (`POST /:id/merge-into/:targetId` есть в
коде, но без кнопки), поэтому исправить уже разъехавшиеся накладные нечем.

Это не сбой, а намеренно узкие окна склейки + отсутствие ручного исправления.

## Решение (подход A)

Проактивно подсвечивать вероятный дубль-страницу на детальной странице и давать
склейку в один клик. Не трогаем автосклейку (узкие окна оставлены намеренно,
чтобы не сливать случайно разные накладные).

### Компоненты

1. **Детект (бэкенд):** `invoiceRepo.findSiblings(id)` — без временно́го окна и без
   фильтра по статусу.
2. **Отдача:** новое поле `possible_siblings` в ответе `GET /api/invoices/:id`
   (отдельного запроса нет — деталка и так его дёргает).
3. **Баннер (фронт):** над таблицей товаров, по стилю существующего баннера
   дубля.
4. **Действие:** существующий `POST /:id/merge-into/:targetId`.

## Раздел 1 — Правило детекта (`findSiblings`)

Сиблинг = другая накладная, у которой:

- **тот же нормализованный номер** (`normalizeInvoiceNumber` — учитывает
  гомоглифы кириллица/латиница и регистр), И
- **совпадает поставщик** (`suppliersMatch`), И
- **совпадает дата накладной** (`invoice_date`) — **обязательно**, когда она
  есть у обеих. Если у одной даты нет — даём пройти по номеру+поставщику (не
  блокируем из-за пропущенной OCR-даты), но если у обеих дата есть и они разные
  — это НЕ сиблинг (один и тот же номер в разных периодах не схлопывается).

Исключаем:

- саму себя (`id`);
- строки, уже помеченные точным дублем (`duplicate_of IS NOT NULL`);
- накладные без `invoice_number` (слишком ненадёжно для детекта).

**Без** ограничения по времени и по статусу — иначе реальный кейс (обе
«Отправлен», разрыв > 10 мин) не ловится.

Сигнатура:

```ts
findSiblings(id: number): Promise<Array<{
  id: number;
  invoice_number: string | null;
  invoice_date: string | null;
  supplier: string | null;
  total_sum: number | null;
  status: string;
  items_count: number;
}>>
```

Реализация: загрузить накладную; при отсутствии номера вернуть `[]`; иначе выбрать
кандидатов с непустым `invoice_number`, тем же нормализованным номером,
`duplicate_of IS NULL`, `id != :id`; в JS-фильтре проверить `suppliersMatch` и
правило даты; докинуть `items_count` (COUNT по `invoice_items`).

## Раздел 2 — Баннер, направление склейки, обработка «Отправлен»

### Отдача

`GET /api/invoices/:id` дополняется полем `possible_siblings` (массив, обычно 0–1).
Деталь-роут вызывает `findSiblings` и кладёт результат в payload рядом с `items`.

### Баннер

Рендер над таблицей товаров (тот же визуальный язык, что у существующего баннера
`duplicate_of`, — не вводим новый дизайн). Текст-образец:

> ⚠ Похоже на ту же накладную: **#151** (8 позиций, 54 217,60 ₽, статус
> «Отправлен»). Возможно, это страницы одной накладной. **[Объединить →]**

При нескольких сиблингах — по строке на каждого (на практике почти всегда один).

### Направление склейки

Всегда сливаем в накладную с **меньшим id** (первая = страница 1, каноничная по
шапке). Для #151/#159: source=#159 → target=#151. Под капотом —
`POST /:id/merge-into/:targetId` (source=`:id`, target=`:targetId`): items
переезжают source→target, фото переносятся, grand total = max(обоих), source
удаляется, total пересчитывается.

### Обработка «уже отправлена» (решение: предупреждаем, но разрешаем)

Если **хотя бы одна** из двух накладных в статусе `sent`/`approved`, перед
склейкой показываем подтверждение:

> Одна из накладных уже отправлена в 1С. Объединение исправит дубль в ScanFlow,
> но в 1С документ уже создан — лишний нужно удалить вручную.

Кнопки: «Всё равно объединить» / «Отмена». Сама склейка **не блокируется** —
иначе реальный кейс (обе отправлены) не починить; риск проговаривается явно.
Если ни одна не отправлена — склейка идёт без доппредупреждения (обычный confirm).

### После склейки

Перезагрузка деталки (`this.showDetail(id)` на каноничную накладную), как делают
`remap`/`addPages`.

## Тестирование (vitest)

`tests/database/findSiblings.test.ts`:

- ловит сиблинга при совпадении номер+поставщик+дата, **без** временно́го окна
  (создать две накладные «в прошлом» и убедиться, что находит);
- НЕ ловит при разных датах (когда обе даты заданы);
- ловит при отсутствии даты у одной из них (номер+поставщик достаточно);
- игнорирует `duplicate_of IS NOT NULL` и безномерные;
- игнорирует саму себя.

`tests/api/mergeBanner.test.ts` (или дополнение существующего invoices-теста):

- smoke: при наличии сиблинга `GET /:id` отдаёт `possible_siblings` с верным id;
- merge через `merge-into` схлопывает две строки в одну, items суммируются,
  total = max.

Все тесты — только против `localhost`/тест-БД (sanity-guard в `tests/helpers/db.ts`).

## Что НЕ делаем (YAGNI)

- Не расширяем окно автосклейки и не разрешаем авто-склейку в отправленные
  (вариант C отклонён — риск ложных слияний и порча уже созданного в 1С).
- Не делаем общий пикер «объединить с любой накладной» (вариант B) — детект по
  тройной подписи покрывает реальную боль; пикер можно добавить позже отдельно.
- Не трогаем существующую систему точных дублей (`duplicate_of`).
