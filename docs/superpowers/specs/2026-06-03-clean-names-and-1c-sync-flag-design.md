# Очистка имён номенклатуры + флаг выгрузки в 1С — дизайн

**Дата:** 2026-06-03
**Статус:** утверждён к реализации
**Автор:** Claude (по брифу владельца)

## Контекст и проблема

Две независимые, но связанные задачи, обе про корректную передачу новой номенклатуры в 1С:

1. **Грязные имена у несопоставленных позиций.** У каждой позиции два имени: `original_name`
   (сырой OCR-скан) и `mapped_name` (колонка «Название (1С)»). Для позиций, **сопоставленных**
   с каталогом 1С, в `mapped_name` лежит каноничное имя из каталога — всё хорошо. Для позиций
   **«Не найдено»** (`source: 'none'`) сейчас `mapped_name = original_name`, т.е. сырой скан
   с хвостами вида `3-4кг`, `d120`. 1С-обработка
   ([ObjectModule.bsl `НайтиИлиСоздатьНоменклатуру`](../../../1c/КНД_ЗагрузкаНакладныхСканер/КНД_ЗагрузкаНакладныхСканер/Ext/ObjectModule.bsl#L861))
   создаёт новую `Справочники.Номенклатура` ровно из этого текста → в 1С появляются товары
   с мусорными именами. Пример: `Ветчина с бедром индейки вареная 3-4кг d120`.

2. **Нет сигнала «нужно выгрузить каталог обратно».** Когда на сайте одобряют накладную
   с новыми позициями, 1С при загрузке создаёт под них новую номенклатуру, но кэш каталога
   на сайте (`onec_nomenclature`) об этом не знает. Нужен лёгкий флаг, по которому регламентное
   задание 1С раз в минуту понимает, что появились новые товары, и выгружает каталог обратно —
   но не гоняет тяжёлую выгрузку вхолостую, когда новых товаров не было.

Существующая `normalizeName()` в [nomenclatureMapper.ts](../../../src/mapping/nomenclatureMapper.ts#L78)
используется **только для нечёткого сопоставления**, не для имени, которое уходит в 1С, и не ловит
калибр `d120`. Существующая авто-выгрузка после загрузки накладных уже есть, но срабатывает по
факту «создан ≥1 документ», а не по факту «были новые товары».

## Принятые решения (из брифа)

- **Очистка имени:** regex-обрезка хвостов (детерминированно, без вызова LLM).
- **Куда писать:** в редактируемое поле «Название (1С)» (`mapped_name`) для несопоставленных позиций.
  Пользователь видит результат и может поправить до отправки.
- **Флаг:** глобальный «нужна выгрузка номенклатуры», ставится при отправке в 1С накладной
  с новыми (несопоставленными) позициями; 1С читает его по расписанию и сбрасывает через API.
- **Сторона 1С:** три отдельные функции (ручная выгрузка, ручная загрузка, новая — по расписанию).
  Функция по расписанию делает **полный цикл**: загрузка → (по флагу) выгрузка → сброс.

## Часть A — Очистка имён несопоставленных позиций

### A.1 Новая функция `cleanItemName`

Новый файл `src/mapping/nameCleaner.ts`, экспорт `export function cleanItemName(raw: string): string`.
Чистая, без побочных эффектов, идемпотентная, покрыта юнит-тестами.

**Философия:** консервативная обрезка **хвостового** мусора размера/фасовки/калибра. Функция НЕ
пытается ужать многословное имя до «ядра» (`Сельдь филе Классическая в масле` остаётся как есть —
свести к `Сельдь филе` это работа сопоставления с каталогом, а не обрезки).

**Срезает:**

| Категория | Примеры | Эскиз правила |
|-----------|---------|---------------|
| Калибр/диаметр | `d120`, `д120`, `ø60`, `d 120` | токен `[dдøØ]\s?\d{2,3}` на границе слова |
| Вес/объём + диапазоны | `3-4кг`, `0,5 л`, `500г`, `10шт` | `\d+(?:[.,]\d+)?(?:\s?[-–—]\s?\d+(?:[.,]\d+)?)?\s*(?:кг\|гр\|г\|мл\|л\|шт\|уп\|упак\|пач\|бут)\.?` |
| Хвостовые одиночные числа | `… вареная 3` | число (или диапазон) в самом конце строки |
| Хвостовые слова фасовки | `пэт`, `в/у`, `б/у`, `вакуум…`, `ведро`, `лоток`, `пакет` | маленький белый список, только в конце |

**Сохраняет (критично):**

- **`%`** — жирность `3,2%`, `45%` это реальный различитель товара. Правило веса требует единицу
  (кг/г/л/мл/шт/…), а `%` единицей не считается, поэтому `3,2%` не трогается. Обрезка хвостового
  одиночного числа применяется только если последний символ — цифра, поэтому `…3,2%` тоже цело.
- Описательные слова в середине (`Классическая в масле`, `копчёная`, `охл`).
- `original_name` (колонка «Скан») — **никогда не меняется**, это отдельная колонка.

**Свойства:**

- **Идемпотентность:** применяется в несколько проходов до стабилизации (повторный вызов
  на результате не меняет его).
- **Не возвращает пусто:** если очистка обнулила бы строку или оставила < 2 символов — откат
  к исходному `raw`.
- В конце: схлопывание пробелов, trim, срез хвостовой пунктуации `[\s,.;–-]+$`.

Точные регулярки финализируются тестами (см. A.4). Список слов фасовки и набор единиц вынести
в именованные константы рядом с функцией, чтобы владелец мог их править.

### A.2 Точка встраивания (DRY)

Единственная правка в логике — в [`NomenclatureMapper.map()`](../../../src/mapping/nomenclatureMapper.ts#L149),
ветка «3. None»: вместо `mapped_name: scannedName` вернуть `mapped_name: cleanItemName(scannedName)`.

Все пути загрузки потребляют `mapping.mapped_name`, поэтому очистка применится автоматически и без
дублирования:

- [fileWatcher.ts](../../../src/watcher/fileWatcher.ts#L367) — три точки ингеста.
- [dispatcher.ts:442](../../../src/api/routes/dispatcher.ts#L442).
- [Маршрут пересопоставления](../../../src/api/routes/invoices.ts#L616).

Сопоставленные позиции (`source: 'learned' | 'onec_fuzzy' | 'legacy'`) не затрагиваются — у них
`mapped_name` берётся из каталога.

### A.3 Ретроактив для старых строк

В маршруте `POST /:id/llm-remap`/remap ([invoices.ts](../../../src/api/routes/invoices.ts#L606))
добавить ветку для `result.source === 'none'`: если `cleanItemName(original_name)` отличается от
текущего `mapped_name`, обновить через `invoiceRepo.updateItemMappingName(item.id, cleaned, 0)`.
Тогда кнопка «Пересопоставить» чинит уже загруженные ранее накладные.

### A.4 Тесты (`tests/mapping/nameCleaner.test.ts`)

- `Ветчина с бедром индейки вареная 3-4кг d120` → `Ветчина с бедром индейки вареная`
- `Молоко 3,2% пакет` → `Молоко 3,2%` (жирность цела — `%` обязан остаться; `пакет` в белом
  списке хвостов фасовки → срезается)
- `Сельдь филе Классическая в масле 3 кг ведро` → `Сельдь филе Классическая в масле`
  (`3 кг` и `ведро` срезаны, описание цело)
- `Колбаса д80` → `Колбаса`
- Идемпотентность: `cleanItemName(cleanItemName(x)) === cleanItemName(x)`
- Откат: строка только из веса (`3 кг`) → возвращает исходное, не пусто
- Сохранение `%`: `Сметана 20%` → `Сметана 20%`

## Часть B — Флаг «нужна выгрузка номенклатуры»

### B.1 БД — миграция 33

Текущий максимум миграции — 32 ([migrations.ts](../../../src/database/migrations.ts)).
Новая миграция 33 (идемпотентная, `CREATE TABLE IF NOT EXISTS`):

```sql
CREATE TABLE IF NOT EXISTS integration_sync_state (
  id TINYINT NOT NULL PRIMARY KEY DEFAULT 1,
  nomenclature_sync_requested_at DATETIME NULL,
  CONSTRAINT chk_sync_state_single CHECK (id = 1)

INSERT IGNORE INTO integration_sync_state (id, nomenclature_sync_requested_at) VALUES (1, NULL);
```

Однострочная таблица состояния (тот же паттерн, что у `analyzer_config` / `webhook_config`).
`detect()` миграции: проверить наличие таблицы для бэкфилла.

### B.2 Репозиторий `syncStateRepo`

Новый `src/database/repositories/syncStateRepo.ts`, методы (все async, как требует п.15 CLAUDE.md):

- `markNomenclatureSyncRequested(): Promise<void>` — `UPDATE … SET nomenclature_sync_requested_at = NOW() WHERE id = 1`.
  Всегда двигает метку вперёд (на каждое срабатывание), чтобы `since` отражал самый свежий триггер.
- `getNomenclatureSyncState(): Promise<{ requested: boolean; since: Date | null }>`.
- `clearNomenclatureSync(since: Date): Promise<{ cleared: boolean }>` —
  `UPDATE … SET nomenclature_sync_requested_at = NULL WHERE id = 1 AND nomenclature_sync_requested_at <= ?`.
  Возвращает `cleared` по числу затронутых строк. Гард `<= since` = защита от потерянного обновления.

### B.3 Кто ставит флаг

В [`POST /api/invoices/:id/send`](../../../src/api/routes/invoices.ts#L384), после `approveForOneC(id)`:
если накладная содержит ≥1 позицию с `onec_guid IS NULL` → `await syncStateRepo.markNomenclatureSyncRequested()`.

- Добавить `invoiceRepo.hasUnmatchedItems(id): Promise<boolean>`
  (`SELECT 1 FROM invoice_items WHERE invoice_id = ? AND onec_guid IS NULL LIMIT 1`).
- Записать событие в «Журнал интеграций» через `logIntegrationEvent`
  (`integration: 'nomenclature'`, `event_type: 'sync_requested'`,
  summary: «Накладная №… содержит новые позиции — каталог 1С помечен к выгрузке»).
- Ложноположительные безвредны: если несопоставленная позиция на самом деле уже есть в 1С
  по имени, лишняя выгрузка просто обновит каталог.

### B.4 Эндпоинты (роутер `/api/integrations`, авторизация `X-API-Key`)

Добавить в [integrations.ts](../../../src/api/routes/integrations.ts):

- `GET /api/integrations/sync-flag` →
  `{ data: { nomenclature_sync_requested: boolean, since: string | null } }`.
  Лёгкая проверка для регламентного задания.
- `POST /api/integrations/sync-flag/clear`, тело `{ since: string (ISO) }` →

## Часть C — Сторона 1С (BSL)

Три отдельные команды/функции. Ядро загрузки выносится в общий хелпер, чтобы не дублировать
логику и не выгружать каталог дважды.

### C.1 Рефакторинг: вынести ядро загрузки

Из текущей [`ЗагрузитьНакладныеСоСканера`](../../../1c/КНД_ЗагрузкаНакладныхСканер/КНД_ЗагрузкаНакладныхСканер/Ext/ObjectModule.bsl#L116)
вынести **чистую загрузку** (GET /pending → создание документов → фото → confirm) в новую
функцию `ЗагрузитьНакладныеИзPending()`, возвращающую структуру
`{ Создано, Ошибок, Отчёт }`. **Без** авто-выгрузки номенклатуры внутри.

### C.2 Функция «Загрузить накладные со сканера» (ручная, существует)

`ЗагрузитьНакладныеСоСканера` теперь:
1. `ФлагSince` = прочитать флаг (см. C.5), не падать при ошибке.
2. `Рез = ЗагрузитьНакладныеИзPending()`.
3. Если `Рез.Создано > 0` → `ВыгрузитьНоменклатуруНаСайт()` (как сейчас).
4. Если выгрузка прошла и `ФлагSince` заполнен → `СброситьФлаг(ФлагSince)`.

Поведение для пользователя сохраняется (одна кнопка грузит и подтягивает каталог), плюс корректно
гасит флаг.

### C.3 Функция «Выгрузить номенклатуру на сайт» (ручная, существует)

[`ВыгрузитьНоменклатуруНаСайт`](../../../1c/КНД_ЗагрузкаНакладныхСканер/КНД_ЗагрузкаНакладныхСканер/Ext/ObjectModule.bsl#L1367)
— **без изменений**. Произвольный запуск, выгружает всё по выбранным категориям, флаг не трогает
(она не грузит накладные, поэтому не гарантирует, что новая номенклатура уже создана — гасить флаг
ей нельзя).

### C.4 НОВАЯ функция «Автосинхронизация (расписание)»

Новая зарегистрированная команда `КНД_АвтосинхронизацияПоФлагу` (см. `СведенияОВнешнейОбработке`
и `ВыполнитьКоманду`). Это единственное, что ставится регламентным заданием раз в минуту.

Алгоритм:
1. **Шаг 0:** `ФлагSince`, `ФлагСтоит` = прочитать `GET /api/integrations/sync-flag`.
   При ошибке запроса — `ФлагСтоит = Ложь`, дальше работать как обычная загрузка.
2. **Шаг 1:** `ЗагрузитьНакладныеИзPending()` — **всегда**. Создаёт документы и новую номенклатуру.
   Пустая очередь → 0 документов, дёшево.
3. **Шаг 2:** если `ФлагСтоит` → `ВыгрузитьНоменклатуруНаСайт()`.
4. **Шаг 3:** если выгрузка в Шаге 2 прошла успешно → `СброситьФлаг(ФлагSince)`
   (`POST /sync-flag/clear` с `since` из Шага 0).

**Порядок (обоснование):** новая номенклатура создаётся только в Шаге 1, поэтому выгрузка (Шаг 2)
обязана идти после загрузки. Функция самодостаточна — на расписание ставится только она.

**Крайние случаи:**
- GET флага упал → выгрузку пропускаем, флаг не трогаем, следующая минута повторит.
- Выгрузка упала → флаг НЕ сбрасываем → авто-повтор на следующей минуте (самовосстановление).
- Очередь пуста, но флаг стоит (прошлая выгрузка не дошла) → Шаг 1 создаёт 0 документов,
  но раз флаг стоит — Шаг 2 всё равно выгружает и Шаг 3 гасит. Долг закрывается.
- Гонка: одобрение новой накладной во время Шагов 1–2 двигает метку флага вперёд; `clear(since)`
  с гардом `<= since` её не затрёт → флаг остаётся → доработается следующей минутой.
- Двойной запуск: `confirm` идемпотентен, `sync` = полная замена каталога (DELETE+POST) → повтор безвреден.

### C.5 Хелперы доступа к флагу (BSL)

- `ПрочитатьФлагВыгрузки()` → структура `{ Стоит: Булево, Since: Строка }` через
  `GET /api/integrations/sync-flag`. Все ошибки гасятся в `{ Стоит: Ложь, Since: "" }`.
- `СброситьФлагВыгрузки(Since)` → `POST /api/integrations/sync-flag/clear` с телом
  `{"since": "<Since>"}`. Использует существующий паттерн `СоздатьHTTPСоединение` / `ОтправитьДляОбработки`.

## Риски и заметки

- **Обрезка калибра/веса лосси:** два товара, отличающиеся только `d120` vs `d80` или `3кг` vs `5кг`,
  схлопнутся в одно имя в 1С. Это сознательно (одна карточка на семейство товара). Если понадобится
  иначе — менять белые списки в `nameCleaner.ts`.
- **Сохранение `%`** — обязательная инвариантность очистки, закрыта тестом.
- **Тесты и БД:** любые тесты с DDL/TRUNCATE обязаны идти через guard `tests/helpers/db.ts`
  (п.17 CLAUDE.md) — иначе не запускаться.
- **`detect()` миграции** обязателен для бэкфилла (конвенция проекта).
```
