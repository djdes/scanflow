## 1. Выключить движок (без выкладки, мгновенно)

движок = прежнее поведение кода.

| Что не так | Выключить |

| Лишние красные строки «цена выбивается» | «Проверка цены за единицу» (`price_guard`) |
| Подбор позиций 1С стал хуже | «Сопоставление v2» (`mapping_v2`) |

## 2. Одна накладная

- **Номер, дата, сумма, НДС.** Карточка накладной → вкладка «История» →
  снимок «как распознано» или «на момент обновления» → «Вернуть номер,
  дату, сумму и НДС». Строки накладной не меняются.
- **Строка.** Под количеством: «↺ как в накладной» — вернуть количество,
  единицу и цену как напечатано; «↻ пересчитать» — заново перевести в
  единицу 1С; «📌 запомнить» — закрепить пересчёт для товара у поставщика.
- **Кто что менял.** «История» показывает журнал правок (`edit_log`): кто,
  когда, было → стало.

## 3. Номер, дата, сумма, НДС — массово

Администратор, `POST /api/debug/restore-headers`. По умолчанию — только
показать, что изменится (`dry_run: true`):

```bash
curl -s -X POST https://scanflow.ru/api/debug/restore-headers \
  -H "X-API-Key: <ключ администратора>" -H "Content-Type: application/json" \
  --data-binary @body.json
```

`body.json`:

```json
{ "kind": "baseline", "invoice_ids": [194, 676], "fields": ["total_sum", "vat_sum"], "dry_run": true }
```

- `kind`: `baseline` (как было до обновления) или `recognized` (как распознано);
- `invoice_ids` — лучше перечислять: без него берутся ВСЕ накладные, и
  откатились бы и правильные ручные правки, сделанные после обновления;
- `fields` — любые из `invoice_number`, `invoice_date`, `total_sum`, `vat_sum`;
- посмотреть ответ, затем то же с `"dry_run": false`. Каждое изменение
  пишется в журнал правок.

## 4. Правила

- **Правило пересчёта** «товар + поставщик»: «Справочники → Предложения
  правил → Правила пересчёта» → снять «Действует». Уже пересчитанные строки
  не меняются (шаг 2).
- **Сопоставление**: «Справочники → Номенклатура» — изменить или удалить;
  метка источника показывает, откуда правило (подтверждено, ИИ,
  восстановлено…).
- **«Не это»**: там же, «Отклонённые варианты» → снять.
- **Вернуть правила из резервной копии**: «Номенклатура → Вернуть правила
  из резервной копии» (только администратор). Файл готовится из SQL-дампа:

  ```bash
  npx ts-node --transpile-only src/scripts/restore-mappings-from-dump.ts <дамп.sql> > rows.json
  # для дампов после разделения по компаниям:
  npx ts-node --transpile-only src/scripts/restore-mappings-from-dump.ts <дамп.sql> nomenclature_mapping_cards --owner=1 > rows.json
  ```

  «Проверить» показывает, что вернётся; «Вернуть» — применить. Возвращаются
  только недостающие правила с позицией в текущем каталоге; существующие не
  меняются. Для `.sql.gz` сначала распаковать.

## 5. Откат кода (крайняя мера)

Схема v2 только добавляет таблицы и колонки — код до v2 с ней работает:

- правила единиц «для товара» хранятся как `item_unit_item` (миграция 73) —
  старый код их не видит и не применит ко всем строкам поставщика;
- ⚠️ старый код при выгрузке каталога из 1С снова **удаляет** сопоставления,
  чья позиция пропала из каталога (v2 их только помечает). Пока откат
  действует, каталог лучше не выгружать;
- модуль 1С (`.epf`) менять не нужно: поле `new_item` старый сервер просто
  не отдаёт.

Как: `git revert -m 1 <merge-коммит релиза>` (или вернуть `main` к тегу
`backup/pre-v2-2026-09-29`) → push в `main` → GitHub Actions выложит сам.
Миграции назад не откатываются, и это не нужно.

## 6. Полное восстановление базы (последняя мера)
